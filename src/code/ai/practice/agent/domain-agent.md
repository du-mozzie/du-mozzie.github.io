# 如何设计一个具体领域的 Agent：通用面试骨架（结束语）

> 场景题："如果让你设计一个 XX Agent，你会怎么做？"——把前面全部内容串成一套通用回答框架。初级工程师答清"大模型 + Tool + RAG"即可；高级岗位必须体现工程复杂度。

## 整体架构：优先主 Agent + 多个领域子 Agent

- 主 Agent：用户理解、任务规划、上下文管理、任务调度；
- 子 Agent：按业务拆分（检索 Agent、推荐 Agent、售后 Agent、执行 Agent…）。
- 为什么用多 Agent：**不同业务域需要的 Spec、Context 和 Tool 差异大，用子 Agent 做隔离**——一句话解释即可，别展开细节。
- 注：实践不推荐多 Agent，面试喜欢；同微服务一样是"面试口味"。

## 六站式回答骨架

**第一站：输入规范化**（收到输入别急着执行）
指代消解、省略补全、口语/病句/黑话/缩写、"更划算/更高级/最近"类需解释的表达。埋面试钩子："我们还专门处理过跨多轮指代，以及性价比这种需要结合上下文、用户画像甚至工具结果才能量化的表达。"说完就停，被追问再展开。

**第二站：意图识别**（不能只是调用一次大模型）
意图识别决定后续加载什么 Spec、组织什么 Context、开放什么 Tool、进入什么业务流程。输出是结构化结果（Intent + 参数），缺参数澄清、不支持拒识、不硬塞。刷亮点：意图多时先召回候选意图再做最终识别。

**第三站：Plan + ReAct 混合形态**
Plan 决定总体目标、步骤和依赖；执行到具体步骤后由 Agent 根据 Observation 动态选 Action。带出 G4C，但只说一句：**Plan 不是简单步骤列表，而是一个能够检查和纠偏的运行时对象**。

**第四站：主动提 Replan**
Plan 执行中上下文变化、假设不成立、工具不可用、Checkpoint 不过 → 进入 Correction。**Correction ≠ 重新生成整个 Plan**：优先 Retry → 当前步骤调整 → 局部 Replan → 回滚 Checkpoint → 逼不得已才全局 Replan。亮点补充：严重依赖外部工具的关键步骤先做最小化 Try，确认关键依赖成立再正式扩大执行（TCC 不要主动全讲，等追问）。

**第五站：上下文管理**（讲了 Plan/ReAct/多轮却完全不谈 Context 会显得奇怪）
结合业务举例：短期 Context = 最近对话/当前 Goal/Plan/Step/约束/工具结果；长期 Context = 历史对话/历史任务/用户画像/长期事实。上下文不能无限塞 → 筛选、压缩、摘要；原始细节保留，需要时召回。
**C 端 Agent 主动提用户画像**：区分短期偏好与长期稳定偏好，不会因为偶尔一句话永久修改画像——这句引导面试官追问"怎么区分临时与长期偏好"，进入画像 4C 等内容。

**第六站：检索**（不要直接背 Embedding/向量库/TopK/Rerank）
先讲 Agent 能查什么（业务知识库、历史对话、用户画像、业务数据库、实时状态、外部搜索、历史任务结果）；再讲核心思想：**不是拿用户原话直接搜，而是根据当前 Goal 和 Plan 判断还缺什么信息，决定查什么、去哪里查**。入库侧：Chunk、层次文档、元数据、权限；检索侧：向量、关键词、结构化查询、多路召回、Rerank。细节等追问。

**可观测性一句带过**：整条链路有 Trace，把 Intent、Plan、Action、Observation、Context 变化、检索证据、Replan 串起来；采集任务成功率、工具成功率、Replan 率、用户纠正率等指标——让面试官知道不是黑盒。

## 通用话术模板（替换业务名即用）

> "我会设计一个主 Agent 加多个子 Agent 的架构。用户输入进来后，先做输入规范化，理解用户到底要什么；然后做意图识别，决定进入哪个业务流程、加载什么 Spec 和上下文。对于复杂任务，主 Agent 先生成 Plan——一个可检查可纠偏的运行时对象，包含目标、上下文、候选路径、检查点和纠错机制；执行中如果上下文变化或假设不成立，会触发 Replan，优先重试和局部调整，而不是重新生成整个计划。整个执行过程采用 Think-Action-Observation 的受控循环，每轮根据当前缺口决定下一步。上下文会区分短期和长期：短期放当前对话、目标、约束和工具结果，长期放历史对话和用户画像；放不下的做压缩和摘要，细节保留索引需要时召回。检索方面，会先明确需要什么信息、去哪里查，再决定用向量、关键词还是结构化查询。最后整条链路都有 Trace 和指标，出了问题能回溯到具体决策节点。"

（若面试官还没理解，就讲一个完整业务故事串起全部环节。）

## 面试前要准备的证据（骨架不能代替项目经验）

准备一个完整案例，能回答：
1. 用户要完成什么任务？
2. 最初采用什么方案？
3. 方案在哪里失败了？
4. 用什么数据证明失败？
5. 为什么选择现在的架构？
6. 放弃过哪些替代方案？
7. 当前方案增加了什么成本和风险？
8. 工具失败或用户改需求时如何恢复？
9. 怎么评测它真的变好了？
10. 重新做一次会改变什么？

面试后及时复盘：面试官追问了什么、哪里答得含糊、哪些判断缺数据支持。**从"会背 Agent 概念"到"真正具备 Agent 系统设计能力"的分界线，是发现自己哪里还欠缺。**
