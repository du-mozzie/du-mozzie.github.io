# 规划执行：Plan / Replan / TAO

## 一、Plan 机制与 G4C

### Plan 的本质

**Plan 不是步骤列表，而是一个可检查、可纠偏、可执行的运行时对象。** 其本质是解决执行中的不确定性。

不确定性来源（也是执行失败的根源）：
- **目标不确定性**：用户要什么、什么叫成功——目标不定，执行越努力偏得越远；
- **上下文不确定性**："那个项目"指哪个、哪些已确认、哪些要澄清；
- **路径不确定性**：达成目标有多种方式，为什么选这条（后续排查极度依赖"为什么"）；
- **过程不确定性**：执行是否"合法"（是否遵守约束、是否量化）——只能减轻（Checkpoint、Prompt 强调约束），无法根除；
- **失败不确定性**：失败原因无数种，重试/查询/追问/重来怎么选。

Plan 的基本思路看似只有四步：先分析用户需求 → 再收集相关信息 → 然后执行任务 → 最后总结输出。但**步骤只是其中的一个部分，是表现形态、是最终看到的产物；在这之前还有很多的步骤和内部信息需要关注**（正是下面 G4C 要覆盖的内容）。

### G4C：好 Plan 的 5 要素

| 要素 | 核心问题 | 缺失后果 |
|---|---|---|
| **Goal** | 我要达成什么？什么叫成功？ | 目标漂移 |
| **Context** | 当前知道什么？还缺什么？ | 凭空 Plan、幻觉 |
| **Choice** | 为什么这么走？还有哪些路径？ | 机械步骤，无法实时应变 |
| **Checkpoint** | 怎么知道当前步骤对不对？ | 无法及时发现，出错只能重来 |
| **Correction** | 发现偏差后怎么办？ | 无法恢复，只能重来 |

一句话：Goal 解决去哪，Context 解决现状，Choice 解决怎么走，Checkpoint 解决怎么知道走偏，Correction 解决走偏后怎么拉回。

<img src="https://raw.githubusercontent.com/du-mozzie/PicGo/master/images/202608302146567.png" style="zoom:67%;" />

**Goal 要点**：目标要给出"标准"——什么算"适合高级工程师表达"？标准最好由大模型结合知识库/RAG 检索自行定义（专属领域可预置标准）。**形容词是幻觉与不稳定的来源**，要精确定义其内涵。

**Context 要点**：维护 known_facts / missing_info；**硬约束、软约束独立维护，每次调用大模型都放入系统提示词**（系统提示词地位高，上下文再长也不易被忽略）。多轮对话中约束一般通过专门的摘要/约束提取步骤得来，**每一个约束的修改都需要有用户输入作为证据**。

**Choice 要点**：输出候选路径 + 选择理由（evidence-based）；steps 可加 reason 字段便于排查。

**Checkpoint 要点**（最易被忽略）：① 执行中防止偏离（每个检查点输出明确检查结果 + 证据）；② 为 Replan 和根因查找提供依据。粒度参考：每次业务逻辑上达到新状态、关键中间步骤完成、容易出错的步骤之后。可用"检查点数量 = 步骤数 / 3"之类的规则定义"足够"。

**Correction 要点**：重试（当前步骤/局部/从头，工具偶发失败/格式错误/超时重试即可）、Replan（认定 Plan 本身有问题）、澄清（提前对缺失/歧义 Context 向用户确认，比瞎答好——错误回答浪费 token）、回滚（数据/状态错误时回滚到某步骤之前，配合 Checkpoint）、中断（不可挽回时告知用户）。可输出结构化 condition→action 映射。

### G4C 结构化落地示例

以下 JSON 是 G4C 各要素在"优化项目经历以适配阿里 Java 后端面试"场景下的结构化输出参考：

**Goal**：目标 + 成功标准（success_criteria）

```json
{
    "goal": {
        "user_goal": "优化项目经历，使其适合阿里 Java 后端面试",
        "success_criteria": [
            "体现技术复杂度", "体现个人贡献", "体现业务价值",
            "能支撑面试官追问", "不虚构用户没有做过的内容"
        ]
    }
}
```

**Context**：known_facts（已确认事实）/ missing_info（缺失信息）

```json
{
    "context": {
        "known_facts": ["用户认为项目偏 CRUD", "目标岗位是 Java 后端", "目标公司是阿里", "用户希望同时生成面试追问"],
        "missing_info": ["项目背景", "技术栈", "业务规模", "用户负责模块", "性能或稳定性数据", "实际做过的优化"]
    }
}
```

**Choice**：selected_path + reason + steps（步骤可带 id/objective）

```json
{
    "choice": {
        "selected_path": "先抽取和补齐项目事实，再生成项目亮点，最后生成面试追问",
        "reason": "如果直接包装，容易违反不能虚构的要求；面试追问应该基于最终项目亮点生成",
        "steps": [
            {"id": "extract_project_facts", "objective": "抽取已有项目事实"},
            {"id": "ask_missing_info", "objective": "追问缺失的关键信息"},
            {"id": "generate_project_highlights", "objective": "生成项目亮点"},
            {"id": "rewrite_project_experience", "objective": "改写项目经历"},
            {"id": "generate_interview_questions", "objective": "基于项目亮点生成面试追问"}
        ]
    }
}
```

**Checkpoint**：按 step_id 绑定检查项

```json
{
    "checkpoint": [
        {
            "step_id": "extract_project_facts",
            "checks": ["是否区分事实和推测", "是否识别出缺失信息", "是否保留用户硬约束"]
        },
        {
            "step_id": "rewrite_project_experience",
            "checks": ["是否存在虚构内容", "是否体现技术复杂度", "是否有量化结果", "是否适配阿里 Java 后端面试"]
        }
    ]
}
```

**Correction**：condition → action 映射

```json
{
    "correction": [
        {"condition": "缺少关键项目信息", "action": "向用户澄清"},
        {"condition": "生成内容包含未经确认的事实", "action": "回滚到事实抽取阶段"},
        {"condition": "用户否认某个技术点", "action": "删除该技术点并局部 Replan"},
        {"condition": "面试追问无法从项目经历中推导", "action": "重新生成项目亮点或降低表达强度"}
    ]
}
```

### Prompt 要点

1. **给出非常明确的目标**，对形容词有清晰的标准，可支持去 RAG / 知识库检索已定义好的标准；
2. **强调约束**：多轮对话中约束通过专门的摘要/约束提取步骤得到，约束的每次修改都要有用户输入作为证据；
3. **生成 Plan 步骤时强调输出路径 + 选择理由**，方案必须有根据（evidence-based）；
4. **检查点粒度**：业务逻辑上每次达到新状态、关键中间步骤完成、容易出错的步骤之后；
5. **纠偏机制**：在提示词中列举不同的业务失败场景及对应的纠偏做法。

### 评估 Plan 质量

- **离线分析**（LLM as Judge）：围绕 G4C 展开细粒度评测——是否违反约束（尤其硬约束）、Context 是否完整、Choice 是否有依据、检查点是否足够（可抽样）。
- **线上指标**：

| 指标 | 解释 |
|---|---|
| Plan 完成率 | 按 Plan 完成任务的比例（可通过 Prometheus 监控） |
| 步骤成功率 | 每个步骤执行成功率（Prometheus 监控） |
| 重 Plan 触发率 | 执行中需要重 Plan 的比例（Prometheus 监控） |
| 用户纠正率 | 用户说"不是这个意思/你理解错了"的比例，需在用户输入后引入评估/观察步骤 |
| 最终任务成功率 | 用户目标是否达成；注意 Plan 完成 ≠ 任务成功 ≠ 达成用户目标，但一般任务完成说明 Plan 质量不错 |

### 高级方案

- **迭代式 Plan 生成**：生成→评估→修正循环，引入 Plan Verifier，相当于给 Plan 做一次 Code Review；控制最大循环次数并监控平均循环次数。Plan Verifier 输出示例（score 需要给出评分标准，否则只能让大模型自由发挥）：

```json
{
    "score": 0.78,
    "goal_issues": [],
    "context_issues": ["没有识别出用户实际负责模块缺失"],
    "choice_issues": ["当前Plan直接生成项目描述，存在虚构风险"],
    "checkpoint_issues": ["缺少事实一致性检查"],
    "correction_issues": ["没有定义用户否认技术点后的回滚策略"],
    "suggestions": ["先追问用户实际负责内容", "增加事实一致性检查", "增加局部 Replan 条件"]
}
```

- **DAG 式 Plan**：要求大模型先识别步骤间依赖关系，再生成 DAG；Prompt 要写明依赖识别规则、反常规例子、**循环依赖检查（最终用代码检查，模型易错）**；线性 Plan 简单可靠，非面试场景够用。

```json
{
    "nodes": [
        {"id": "generate_highlights", "depends_on": ["extract_project_facts", "analyze_target_role"]}
    ],
    "edges": [
        {"src": "extract_project_facts", "dst": "generate_highlights", "attrs": {}}
    ]
}
```

（少数依赖关系带属性的场景，可使用 edges 结构。）

## 二、Replan（上）：触发时机、粒度与控制

### 定义

Replan = 执行中，基于新的 Goal/Context/Choice/Checkpoint 结果，对原计划进行**受控修正**。三个关键词：**执行中、新信息、受控修正**。它是 Correction 的一种实现（Retry / Clarify / Rollback / Replan / Interrupt）。

### 触发时机

工具调用失败、上下文发生变化（多轮补充约束）、违反假设（工具成功≠计划可推进，数据/状态可能不对）、中间结果质量差。注意：**发现需要 Replan → 执行 Replan 至少分两步**，不要在一次调用里同时完成判定与执行。

### Replan 粒度（四种）

当前步骤 Replan（前序结果可信）→ 局部 Replan（回溯若干步骤）→ 全局 Replan（从头）→ 跨轮次 Replan（错误事实跨多轮污染摘要/画像/关键事实表）。
原则：**最小化 Replan 范围，尽可能复用已有结果**；但过度复用会掩盖错误中间结果。

### 触发后的判定

代码 + 大模型双重判定是否需要 Replan：能用代码过滤的（异常分类、if-else/责任链）就不要调大模型——稳定、迅速、省 token。判定思路：该错误能否通过 Replan 绕开/克服（如替代工具）；或"默认都可 Replan + 迭代补充不可 Replan 场景"。

### Replan Prompt 要点

- 带上 **G4C 内容**：原目标与是否变化（没变就不要全局 Replan）、新增信息、哪条 Checkpoint 没过 + 证据；
- **再次强调约束/Spec**（放 System Prompt）；
- **分类输出 + 证据**：保留/修改/取消哪些步骤都要理由；金句——"所有 Replan 判断都必须基于 evidence，没有 evidence 不允许声称 Goal/Context/硬约束改变"；
- **明确何时问用户**：关键信息缺失且继续执行违反硬约束/高风险时澄清。三类关键信息：强约束相关、参数缺失会导致执行失败的、关键工具无替代方案；权限/敏感操作在计划阶段就要请求授权。

### Replan 控制信息

记录 max_replan_total / used_replan_total，防止无限重计划。

### TCC Replan（高级，借鉴分布式事务）

局限性强（高失败成本、高外部依赖、高副作用），面试展示用，实践谨慎。

- **Try**：不完整执行新计划，只做最小化验证——找计划最脆弱处（被后续步骤严重依赖、外部工具、失败代价严重、权限/资金/数据写入、历史常失败），验证工具可用性/数据可获得性/核心假设/关键依赖；必须低成本、低副作用（dry-run 思想）。
- **Confirm**：确认后执行，把 Try 结果写入上下文（Try 产物可复用）。
- **Cancel**：回滚 Try 的临时状态/数据（放临时空间便于清理）、标记失败假设与不可用工具、再次 Replan 或中断。
- 判定是否还能 Replan = 是否还有"替代"的可行方案，无路可走即终止。

## 三、Replan（下）：失败回溯——找对"病根"再下刀

### 四个关键概念

- **失败点**：错误暴露的位置（工具报错、Checkpoint 未过、中间结果偏差）。≠ 根因点，只说明"这里出问题了"。
- **根因点**：最初引入错误事实/假设/路径的位置，可能离失败点非常远。
- **回滚点**：系统状态需要恢复到的位置（一般是某个 Checkpoint），结合根因判定。
- **Replan 起点**：新 Plan 从哪个节点重新生成，可与回滚点重合，也可更早（数据实时性要求）。

### 回溯层级（从轻到重）

1. **动作级**：HTTP 超时/JSON 格式错/网络抖动 → 重试即可，不必 Replan（Prompt 约束先重试再回溯）；
2. **步骤级**：当前步骤实现路径有问题但前序结果可信 → 换工具/换路径（传统容错）；
3. **阶段性回溯**：整个阶段的输入或中间结果失效 → 回到阶段入口重新规划（每过 Checkpoint 算新阶段，体现 Checkpoint 价值）；
4. **全局 Replan**：否定全部中间结果；
5. **跨轮次 Replan**：错误事实在早前轮次写入、后续被反复使用——要找到最早写入点、哪些结果被污染、摘要/画像/事实表是否被污染，甚至清空上下文恢复。

### 基础方案（失败点反向排查）

**记录每一步关键信息**（输入/输出/使用的上下文/事实与证据/依赖假设/工具及输入输出/Checkpoint 结果）→ **快照问题**：客服退款例子——A 步骤基于"未发货"生成判断，物流状态中途变为"已出库"，旧判断未标记失效，C 步骤沿用导致被拒。快照价值：知道每步决策当时看到的状态。

**中间结果标记可信状态**：Verified（已验证可信）/ Available（暂时可用未充分验证）/ Suspicious / Invalid（确认错误）/ Dirty（自身未必错但依赖了 Invalid）。输出条目同步输出证据（evidence-based）。

**反向排查清单**：当前步骤本身执行错？输入错？上游中间结果仍可信？依赖事实正确？原假设成立？用户目标/约束变化？

### 进阶方案

- **Checkpoint 不一定可靠**："一个 BUG 是 BUG，一堆 BUG 是 Work"——上下文整体有问题时可能欺骗 Checkpoint；代码实现的 Checkpoint 更可信。
- **保留候选路径**：失败后回到 Choice 节点选下一条未尝试路径（快速、省 token），记录失败路径避免 A→A→A 死循环；若失败原因已被修复，可重复尝试（需记录失败原因并检测是否修复）。
- **代码 + 大模型双重根因定位**：大模型负责语义问题（判断业务根因、目标是否变化、新约束影响哪些步骤、中间结果是否可复用、生成新路径）；代码负责确定性问题（遍历 DAG、标记 Invalid/Dirty、找最近 Checkpoint、循环依赖、控制重试次数、执行回滚）。原则：**能用代码就不用大模型**。
- **渐进式扩大回溯范围**：先最便宜、影响最小的恢复；从根因开始每次回溯一个 Checkpoint；可与 TCC 结合（Try 验证新计划可行性，不可行则扩大范围）。
- **跳跃式快速回溯**：问题 → 回溯位置的哈希结构（key=问题，value=位置/新计划），离线分析（LLM as Judge）+ 向量数据库沉淀规律。

### 评估回溯效果（能讲清指标即竞争优势）

- 根因定位准确率（专属领域 80%+，人工标注测试集/故障注入）；
- Replan 起点准确率（是否回退太晚保留错误 / 太早浪费正确结果；"近之则怨，远之则不逊"，拿不准就宁早勿晚）；
- 已有结果复用率（复用可信中间结果比例；不能为复用而复用）；
- Replan 恢复成功率（专属领域 80%+，低于则多半在浪费 token）；
- Replan 振荡率（A→B→A→B 反复切换 = 上下文管理不当：没记失败路径、没明确失败原因、Prompt 没带控制信息）。

实践经验：成功 Replan 结果可拿去微调（效果不明显）；原始 Plan + 成功 Replan 作为 few-shot 可显著提高特定场景 Plan 质量。

## 四、TAO & ReAct：受控的状态循环

### 基本概念与关系

- **ReAct** = Reasoning and Acting 交替：输入→思考→执行→观察→再思考→…→输出。
- **TAO** = Think / Action / Observation。两者关系类似"两阶段提交协议和 XA"，本专栏视为一回事。
- **与 Plan 的关系**：① Plan 决定大方向，TAO 决定眼前一步（推荐）；② 用 TAO 推动 Plan 执行（Checkpoint 是 O 的体现、Replan 是 T 的体现、DAG 分支由 T 决定）。只有 TAO 没有 Plan 会：忘最终目标、局部打转、短期合理长期不合理、重复查询、越走越偏。

G4C ↔ TAO 对应：Goal/Context/Choice → Think；Checkpoint → Observation；Correction → Think。

### TAO 的核心：状态循环（不是三段文字）

- **Goal State**：最终目标 + 当前阶段目标 + 成功标准。TAO 是局部决策，目标状态是防偏航的锚点；每轮 Think 检查：当前 Action 能否推进目标、还差什么、成功标准是否满足、能否停止。
- **Action State**：每个 Action 的类型/工具名/参数/结果，外加时间、时效性、可重试、可回滚等（常读写放 Redis，历史归档 MySQL）。
- **Observation State**：**记录的不是原始返回值，而是对返回值的解释**（new_facts / missing_information / state_changes / anomalies / suggested_next_action / progress 是否取得进展）。接口 200 不代表数据可用，必须把原始结果转成状态变化再判断是否真的前进。
- **Fact State（关键事实，面试专用词）**：已确认事实 / 用户明确认可的 / 未验证推测 / 被否定的 / 当前缺失。**关键事实单独提取、单独存储、Prompt 中单独一块**——摘要会压缩丢细节，长任务不能只依赖摘要。"Agent 就像健忘的妈，必须每天耳提面命"。
- 其他可选项：Evidence State（观点↔证据，说出来≈宣告解决幻觉）、Gap State、Checkpoint State、Control State（防无限循环，实践最重要）。

流程：读取状态 → Think → 选 Action → 执行 → 生成 Observation → 更新状态 → 判断下一步。

### Think / Action / Observation

**Think 五类判断**：目标判断（最终目标 + 当前目标，方向错了知识越多越反动）；状态判断（缺啥补啥：事实够否/槽位缺失/未验证假设/事实冲突）；路径判断（有哪些 Action 可用）；停止判断（成功标准满足/关键信息足够/继续能否明显提质/是否超预算/是否先返回阶段性结果——停在两个极端都不好）；风险判断。

**Action ≠ 工具 ≠ 接口**：Action 是二次封装的产物，可封装外部工具、内部接口、聚合多接口，也可以是与用户的交互（政务 Agent 要求放身份证）。万物皆可 Action。

**Observation：存储 + 解读，解读更重要**。结构化内容：Action 是否成功、获得哪些新事实与证据（遏制幻觉）、是否符合预期、还缺什么、是否异常、是否违反约束、是否推翻假设、状态变化、是否取得实际进展。存储用代码，复杂语义解读用大模型。

### TAO 六个出口

Continue（目标未完且有可用 Action）/ Finish（成功标准满足）/ Clarify（缺关键信息且猜测违反硬约束或高风险）/ Retry（偶发失败，维持重试次数）/ Replan（路径/假设/工具选择本身有问题，审查上下文后回溯）/ Error/Interrupt（兜底，防无限思考）。

### 双层 TAO 循环（面试推荐）

内层循环执行当前任务（下一步怎么走），外层循环监督方向（Goal 漂移、约束违反——"走得对不对"）。落地：异步，或每 N 轮 / 每次到 Checkpoint 同步执行一次。尤其适合长任务——长任务的问题是小错误不断累积。

### 评估 TAO

- **Think**：动作选择准确率（最重要）、动作参数准确率、当前目标判断准确率、信息缺口识别准确率、约束违反率、停止判断准确率（多靠离线分析 + LLM as Judge）；
- **Action**：执行成功率、响应时间（传统工程范畴）；
- **Observation**：事实提取准确率、证据绑定准确率、工具结果误读率、异常识别准确率、信息缺口更新准确率；
- **整体**：最终任务成功率、平均 TAO 轮数、平均工具调用次数、平均 Token 消耗、任务平均延迟。

面试话术：*"我们没有简单让大模型自由执行 ReAct，而是将它工程化成一个受控的 TAO 状态循环……"*

## 五、Action 设计：为什么总是"选错工具"

### Action 设计基础

- **粒度**：Action 是一个**业务上完整的操作**（内部可调多工具、可启动子 Agent）；尽量**正交**（职责边界清晰），但业务完整性与正交常冲突（"退货并退款" vs "仅退款"重叠退款职责）。
- **子 Agent 作为 Action**：主 Agent 传递完整上下文，子 Agent（通用 TAO 实现 + 启动 Prompt）自行决策使用哪部分。
- **反范式**：粗粒度 Action 减少数量，内部按参数/上下文再细分（配合多次筛选）。
- **可用性**：Action 提供者自己保证高可用（重试/降级/熔断/互为替代工具封装为一个 Action），不寄望 Agent 容错。
- **权限控制**：封装（每个 Action 自己管）或通用鉴权模块/AOP 式（装饰器模式：PermAction 包装 Action 调 permSvc.Check）。RBAC/ABAC 直接套用传统鉴权。

### 候选 Action 数量

面试答案：**3–5 个**（Anthropic 建议；工具 < 10 个可直接全放上下文）。实践：Action 正交、边界清晰就多放也无妨；边界模糊则少量也错。优化准确率时才需要控制数量。

### Action 描述要素

name（命名很重要）、description、applicable_scenarios + inapplicable_scenarios（正反定义边界）、required_params（参数越少越好、越易拿到越好，推理内化为代码）、返回值**最小化**（只暴露调用者需要的，几十种返回值的 Action 该拆）、preconditions（建议代码检查而非让模型判断）、cost、risk、reversible。

### 选择规则

只能从候选 Action 中选择（**枚举 + 代码检查：不仅要存在，还必须是本轮候选**——防大模型从上下文得知旧 Action 而误选）；前置检查用代码/规则引擎；结合 Replan 排除失败选项（注意网络类 Action 可能恢复）；**输出决策理由与证据**（减幻觉、可排查、可沉淀做微调）；few-shot 正反案例（以 Action 名为 key 组织）。

### 海量 Action 解决方案（面试热点）

候选流水线（最后一环是大模型精筛，前面环节用代码或轻量大模型粗筛）：
1. **基于意图组织**：Action 关联意图（Map/关联表），只在该意图下可用；
2. **基于标签**：Action 打标签筛选；
3. **规则引擎**：按上下文状态筛选（缺用户画像时注入加载画像的 Action）；
4. **大模型多次筛选**：海量 Action + 少量上下文（只放目标、缺失数据）粗筛——粗筛不求准；
5. **基于召回**：Action 描述/案例入向量库，召回相关 Action；
6. **前置条件过滤**（无订单 ID 就不给查询订单 Action）、**权限过滤**、**历史成功率过滤**；
7. **基于信息增益/不确定性下降**：从"选最可能完成任务的 Action"改为"选最大程度降低不确定性的 Action"（缺信息时先补信息，防信息缺失就下结论）。

面试话术：证明有很多 Action（业务特征使然，如 RPC 接口即 Action）→ 演进式讲解决过程（先没解决→准确率低→定位到 Action 太多→Anthropic 观点→其他优化措施）。

## 六、面试场景设计：复杂业务场景 = 主线剧情

### 场景要求

多步骤（如**商品推荐**深度结合用户画像；避免"问答"类——面试官会带入 RAG 一次搞定）→ 套入 Plan/TAO："缺啥补啥"构造多轮 TAO（第一轮缺画像→加载；第二轮缺浏览记录→加载；第 N 轮找齐→输出）。

### 加分要素

- **用户交互**：多轮对话 + 第二轮细分场景（"第二条裤子挺好但贵，有没有更有性价比的"）——**突出两轮 Think 决策差异**（画像已加载则跳过、重新解析目标、设计性价比认定规则），证明"自主决策"而非 workflow；
- **执行中纠正**：输出计划后用户插入纠正指令；
- **海量 Action**："几百个工具"挖坑 → 面试官必问怎么选得对 → 用 Action 筛选方案反转；
- **Action 权限控制**：退款退货需要用户确认授权；
- **Action 失败处理**：新用户无价格偏好→兜底策略；接口调不通→降级；数据不全→TAO 循环补全；
- **回溯 + Replan**：失败点≠根因点≠回滚点≠Replan 起点（商品推荐案例：失败点=推荐不符合预算；根因=错误复用电子类目价格偏好；回滚点=已确认画像的 Checkpoint；Replan 起点=重定服装类目价格区间；可复用=品牌/尺码/颜色偏好；需失效=候选商品/排序/推荐结果）→ **受控 Replan**；中间结果记录依赖信息，依赖失效级联标记失效；
- **动态路径**：回答"不就是 workflow 吗"——强调大量**运行时才能确定的决策**（画像完整→直接检索；画像缺失愿交互→询问；不愿补→保守候选集；接口不可用→切缓存；硬约束不满足→重新检索；执行中新增约束→失效已生成候选）。身段要软：初期/赶上线用 workflow 也 OK。

**结论**：复杂业务场景是面试主线剧情，把用户输入规范、意图识别、上下文管理、记忆管理都挂到这条主线上，逻辑性和表达都会显著提升。
