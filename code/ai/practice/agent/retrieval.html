智能检索：不只是 RAG（18–22 讲）

一、Agent 信息检索机制设计（18 讲）

核心观点：RAG 只是 Agent 检索的一部分。 知识库问答、摘要后召回细节、"刚才那个方案"、长任务的工具结果/中间产物/Checkpoint、外部实时数据——都在"检索"范畴。面试别只答"文档切片 → Embedding → Milvus → TopK → Rerank"。

什么时候查 / 查什么（教会 Agent 思考）

两层：开发者设计环节决定要不要查；Agent 运行中自己判断"缺什么查什么"。

"缺什么"的思考模板（结合 Goal Context）：

  1. 明确当前要做的判断（查询是手段不是目的；"LangGraph 适不适合客服 Agent"→ 目标 = "是否满足生产要求"）；
  2. 推导判断所需证据（生产要求 → 任务中断恢复 → 查 LangGraph 中断/恢复功能点）；
  3. 区分已知与未知（已知技术栈是 Python 就不用再问）；
  4. 判断缺口是否值得查（不重要/不影响后续就不查；不查询 = 降级机制）。

去哪里查（可查询空间 Query Space）

不只是向量库：特定 Action、ES 索引、业务数据库、历史对话、用户画像、代码仓库、日志、Trace、外部搜索、Agent 自身中间产物。

可查询空间随任务动态变化：退款第一轮查退款记录 → 发现支付渠道处理中 → 扩展到支付系统 → 银行错误码 → 加入错误码文档/账户信息/渠道规则；可信中间产物（已确认事实、Checkpoint 结果、失败原因、用户认可结论）也可重新进入查询空间。

固定套路两种：

  • 信息由特定 Action 提供 → 规则/业务流程直接绑定（如用户画像 Action），不要让大模型在几十个工具里自由猜；只有"信息可能存在于多处"（接口为什么报错 → 代码/日志/Trace/配置/历史变更）才让 Agent 动态判断；
  • ES/向量库查询 → Index Registry（索引说明）：为每个索引建 profile（index_name、description、suitable_for、not_suitable_for、fields、query_modes、freshness、authority、permissions、update_frequency）。3-5 个索引直接放 System Prompt；几十上百个索引时"先检索索引，再检索数据"（第一次查业务数据之前先从索引说明里召回候选索引；可循环、要控制最大循环次数、每次召回不同候选；实现方式：索引说明入 ES 关键字召回 / 向量化召回 / 打标签 / 业务域划分 / 意图划分 / 权限划分 / 索引树）；候选索引数量可动态调整（剩余窗口大给 10-15 个，小给 3-5 个）——面试亮点。

查询改写（基础 + 复杂）

规则（结合输入规范化）：保留硬约束、提取软偏好并转可查可比指标、消除歧义（领域/历史/画像）、统一术语、删无关信息、从问题转向信息缺口、增加过滤条件（user_id/租户/订单/时间/数据类型）、禁止擅自补充事实、检查查询可执行性、控制查询粒度（一次围绕一个信息缺口）、设置停止条件。

HyDE（假设文档嵌入）：先让大模型生成"可能的答案文档"再向量化去检索——真实文档以"陈述答案"方式写作、用户 Query 以"提问"方式表达，HyDE 缩小语义差距。注意：假想文档不是真实答案，不能当最终证据；要求生成核心概念/标准术语/属性与判断维度/答案结构，避免具体数字版本号。变种：多段回答分别检索后统一重排；先初步回答再针对其中名词生成追问 Query。

5W1H 拆解：What（发生了什么/状态）→ Who（涉及谁）→ When（时间线）→ Where（哪个系统/环节）→ Why（为什么）→ How（怎么执行的）。价值：发现缺什么信息、把模糊问题拆成可独立查询的子问题、建立子问题↔数据源映射（订单号→订单系统、状态→退款记录、渠道→支付系统、错误码→错误码文档、过程→日志 Trace）。不要机械拆全六个维度（"订单现在什么状态"只要 What/Who）；输出结构化 {original_question, sub_questions:[{dimension, question, source}]}。其他拆法：MECE、因果链（根因分析）、时间线（订单/审批）、实体关系。

二、Chunk：召回精度 vs 信息完整性（19 讲）

入库基本流程

采集 → 解析（保留标题/段落/列表/表格/页码结构，解析错了后面无法补救）→ 内容清洗（页眉页脚/广告/重复段落/乱码；扫描版 OCR；表格图片单独解析）→ Chunk 分片 → 补元数据（文档 ID/标题路径/页码/权限/父节点/相邻关系）→ 向量化入库 → 入库校验。

三种基本切法

方式优点缺点
基于长度（+Overlap）简单、稳定、可控不理解内容，可能切断完整定义/条件/案例；Overlap 带来重复
基于语义块内内容集中，适合向量检索成本高、阈值难统一；语义相近 ≠ 业务上应放一起
基于文档结构保留逻辑关系，最推荐依赖解析质量（PDF 标题层级/表格常丢）

推荐混合：结构定大边界 → 语义定内部边界 → 长度兜底。

Chunk Size 怎么定（面试必问）

没有标准答案，三步：

  1. 分析业务最小完整知识单元（客服制度"适用条件+处理规则+例外情况"不能拆；API 方法说明/参数/返回值放一起）→ 统计长度定初始范围；
  2. 结合问题粒度（常查参数/错误码 → 小 Chunk；常要解释/总结 → 大 Chunk 或父子文档）；
  3. 测试集调参（256/512/800/1200 Token 同条件下对比；看正确证据是否召回、证据是否完整、重复内容、最终答案正确率、Token 消耗），并联动 Overlap、Top-K（Chunk 小 → Top-K 大）、父子文档、窗口。选最均衡的一组，不是某指标最高。

话术："先根据业务知识单元确定初始范围，再通过真实问题测试集对 Chunk Size 的召回质量、答案准确率和 Token 成本做对照实验，选最优折中值；实测 600 token 左右最好，线上召回准确率提升 x%。"

特殊内容（按"完整知识单元"切，不按外观）

  • 图片：① 绑定标题/图注/正文作描述 ② 视觉模型生成结构化摘要（OCR 只识别文字，不理解节点关系/箭头/趋势；面试小亮点）③ 同时存原图+文本描述（文本检索，图片作为多模态证据带回）；
  • 长列表：保留共同标题按列表项分组切（每 5 项一块、每块带标题）→ 语义分类聚合 → 父子关系（子节点检索命中后补父标题/相邻项）→ 每项一块；让大模型为列表生成总结独立成块（召回总结并回链列表，很多人忽略，面试创新点）；
  • 表格：小表整表一块（带表名/表头/单位/说明）；长表表头+每行组合（"产品：手机A；价格：3999；库存：有货"）；按业务实体/区域切（部门/产品/年份）；需要聚合筛选排序的大表 → 结构化数据库 SQL 查询；可生成数据规律总结。

层次文档（小粒度找，大粒度读）

父子文档：大父 Chunk + 小子 Chunk；子 Chunk 建向量负责召回，命中后按 parent_id 找回父 Chunk 进上下文。例子：整节退款规则切大块 → "定制商品不支持无理由退货"小子块准确命中 → 把完整退款规则父块交给模型。代价：父块仍可能太大；父块去重（多个子块同父只注入一次）。

基于 RRF 的父 Chunk 排序（面试亮点）：ParentScore(P) = Σ 1/(k + rank(c))，c 为 P 下被召回的每个子 Chunk。子块排名越靠前贡献越大、命中子块越多累计越高；防大父块占便宜：最多取前三个子块/加衰减/加长度惩罚。

层次文档：按结构组织多层（文档→章节→小节→段落→句子/事实），节点记录正文/摘要/标题路径/向量/父子/相邻。标题路径自带语义（最底层"一句话"也知道上下文）；每层可存摘要，检索时可同步检索摘要+原文。物理结构 vs 逻辑结构：按用户查询视角重构层级（产品手册按"安装/配置/故障/性能"而非"第一二三章"组织）——"文档怎么写是作者视角，怎么被检索是用户视角"。

按问题特征选层：事实/参数型 → 段落/事实级；解释/原因型 → 小节级；总结/概览型 → 章节/文档级摘要；对比/综合型 → 多层并行。可规则或大模型判断（"总结一下"→高层；具体参数/错误码→低层）。

逐步扩展：先召回最相关底层块 → 判证据是否足够 → 不够找父节点 → 继续上扩 → 足够或到预算停（缺点：每次判断都调大模型）。实践推荐折中：默认底层检索，按问题类型/充分性/剩余窗口决定是否上扩，总结型直接从高层摘要开始。

三、系统提高召回准确率（20 讲）

检索方式与混合

  • 向量检索：处理同义词/不同表达，但"意思相近 ≠ 含答案"，错误码/型号/版本号精确匹配不稳；
  • 关键字检索（BM25/倒排）：适合错误码/类名/方法名/原文片段精确匹配，但不同表达会漏召回（"退款" vs "撤销订单"）；
  • 图数据库/GraphRAG：实体关系/多跳检索（项目依赖哪些系统、团队归属），构建维护成本高。

多路召回（多种检索策略）+ 多源召回（多个数据源）工程本质相同：多通道候选汇聚统一合并。要点：

  • 各通道 Top-K 可不同（向量噪声多可多召回，关键字集中少召回）；
  • 统一结果结构：内容、来源、文档 ID、Chunk ID、原始排名、原始分数 + 召回方式/更新时间/版本/业务属性；
  • 过滤：权限/租户/时间/用户硬约束直接排除（硬约束决定能不能留下，排序只决定谁在前）；"分数置 0 取代过滤"反范式意义不明，不如直接删；
  • 合并去重：按文档 ID/Chunk ID/内容相似度合并；相邻 Chunk 合并减少 Overlap 重复 token；
  • RRF 混合排序：Score = Σ 1/(k + rank)，不关心原始分数、不同系统分数不可比的问题自然规避，适合第一轮融合；自有加权排序难在分数尺度不可比（豆瓣 8.0 与美团 8.0 含义不同）；
  • 业务规则调整：官方文档优先论坛、当前版本优先历史、实时数据优先旧摘要、用户确认事实优先、标题精确命中加权、高度重复降权。

评估指标

离线：Recall@K（漏没漏，RAG 最重要）、Precision@K（噪声）、Hit Rate@K（出现即命中）、MRR（第一个正确结果位置）、NDCG（相关性等级+位置）、证据覆盖率（复杂问题必需证据召回多少）、重复率。测试集每样本：问题+标准相关文档+标准 Chunk+相关性等级。

线上间接信号：无结果率、追加检索率、用户重新提问率、引用采用率、用户纠错率、人工抽检通过率。关注长尾失败案例（平均分不骗人但骗不了长尾）。

检索结果编辑距离（自定义指标，面试差异化）：标准结果列表 [A,B,C] vs 实际 [A,C,D]，定义操作代价：插入（漏召回，重罚 3）/ 删除（噪声 2）/ 替换（部分相关 2）/ 移动（排序错 1）/ 合并（重复 2）；医疗金融提高错误证据惩罚、复杂问答提高缺失关键证据惩罚。局限：答案顺序不唯一，可标多组可接受结果。

迭代式检索（检索—评估—补充检索循环）

  1. 第一轮：从原始问题/改写 Query 出发，目标不是完整答案而是基本信息（涉及哪些实体、可能方向、已确认事实、缺失信息）；
  2. 判断充分性（关键一步）：各问题部分有无对应证据、能否支持结论、只有结论缺事实、证据冲突、缺时间/版本/对象限制、继续查有无新信息；结构化输出 {sufficient, known_facts, missing_evidence}，missing_evidence 是下一轮输入；
  3. 下一轮 Query：增加关键词/实体、加结构化条件、追查新术语、验证假设、主动查相反证据；
  4. 合并新旧结果：去重、相似降权、新旧版本冲突、可信度差异、动态排序（信息已被覆盖后同类价值降低——排序看"还能提供多少新信息"）；
  5. 停止条件：证据足以回答（结合最小回答原则）、缺口全覆盖、连续两轮无新信息（新增证据 < 阈值）、结果高度重复、查完所有数据源、最大轮数、时间/Token/工具预算、只能向用户澄清；实践设效果+资源双条件；
  6. 记录检索状态：每轮 Query、数据源、召回结果、新增证据、已确认事实、未覆盖缺口、停止原因。

与 Agentic RAG 关系：迭代式检索 = 具体机制（解决"一次没查够怎么办"）；Agentic RAG = 完整系统形态（自主选数据源/工具/路径、验证证据、决定停止）；固定库内重复查询 = 迭代式检索，自主选择数据源与工具 = 接近 Agentic RAG。

四、检索性能优化（21 讲）

性能观（重新定义）

  • 看端到端延迟：用户输入→查询改写→Embedding→多路召回→融合→Rerank→充分性判断→上下文组织→生成，把向量查询 300ms→150ms 对整个链路帮助有限；迭代式检索下链路可能翻倍；
  • 看 P50/P95/P99：平均 800ms 但 P99 3s 不行；多数据源并行查询被最慢者拖住（给慢源设超时/并行+超时控制）；
  • 看吞吐量/并发：QPS、最大并发、连接池、第三方负载；LLM Rerank/Cross-Encoder 并发易成瓶颈；
  • 看成本：模型调用次数/Token/GPU/第三方 API（先把效果做好再考虑成本；效果差 10% 成本减半值得优化）；
  • 性能与准确率一起看：1 秒内 Recall@10、2 秒预算下任务成功率、准确率降 ≤1% 延迟降多少、同准确率下调用次数减半——"功能缩水不是性能优化"。

基础优化（先做这些）

  1. 中间件与索引：ES 按查询条件设计索引/Mapping 避免无效扫描；向量库按数据规模调 ANN 索引参数；租户/权限/时间/类型高频过滤条件提前设计索引——能先结构化过滤（100 万→1 万）就不要直接做向量检索；
  2. 查询优化：Query 带部门/时间范围、只要 10 条别召回 100 条、相似查询合并去重（面试小技巧：中小公司用 ES 做向量检索，讲"从 ES 角度优化向量检索"同时展示两块能力）；
  3. 消除浪费：同 Query 重复 Embedding/重复查询、召回 Top100 只用 Top10、高度重合结果全进 Rerank、能提前算好的不放在线链路（切割/Embedding/关键词/实体/标签/摘要入库阶段完成）。

最小充分检索（面试亮点）

不要试图一次性解决所有问题：找出当前最小的、能独立产生价值的目标，只检索完成该目标需要的信息。 "最小"（不能再拆）+"充分"（完成后能独立给用户价值）是一体两面。

  • 例子：电脑适不适合写代码+哪里买最便宜 → 第一个最小目标 = 判断是否适合写代码，只查配置/需求/评价；不适合则价格/库存都不用查；
  • 判断标准：完成这一件事能否给用户一个有意义的结果（"选最适合放简历的项目"是独立目标；"查询订单"不是——用户要的是退款率，查询只是过程步骤）——不要把过程步骤误认为用户目标；
  • 适用：探索式、多步骤、弱依赖任务（推荐/旅行规划/简历优化/数据分析/问答）；不适用：不可拆独立目标（三年财报判断是否值得投资）、用户要求完整结果（竞品分析报告）、强依赖任务（合同审查/根因分析/完整统计）；
  • 迭代式检索中的"差不多"原则：资源不足/即将超时时，结果已够回答首要问题就中断返回。

基于预算的动态检索（Retrieval Budget）

Budget 维度：剩余时间、最大检索轮次、最大 Query 数、最大数据源数、最大召回/Rerank 数、剩余 Token/窗口。

  • 简单问题 → 关键字或向量直查；复杂 → 混合召回+Rerank；不够 → 查询改写/多路/迭代；
  • 预算下降 → 减少 Query、降 Top-K、减数据源、跳过 LLM Rerank 用当前最好结果；
  • 一句话：先最低成本方案，不够逐步升级，同时检查剩余预算；预算不足主动降级（与上下文动态编排同构）。

缓存

  • 缓存检索结果（推荐）：同 Query+同过滤条件短时间内复用文档 ID/分数/融合排序结果。关键点：先查询改写再找缓存（原始查询差异太大）；用向量库做 KV 缓存（key = 改写后查询的向量，而非文本——改写文本有细微差别）；控制过期；
  • 缓存最终答案（谨慎）：只适合 FAQ/制度/产品说明等答案稳定问题；依赖实时数据/画像/权限/上下文的问题易错——优先缓存检索结果，谨慎缓存答案。
  • 金句：最好的检索性能优化之一，是这一次根本不检索。总纲：能不查就不查，能少查就少查，能复用就复用；不够再逐步扩大。

五、检索（RAG）面试方案（22 讲）

入库有创新

  • 至少准备一个体现思考的点：复杂文档处理（表格/图片/Excel/多级标题/FAQ/代码——挑与业务最相关的一类讲透；视频入库话术可备）、父子文档、层次文档、动态 Chunk（不同文档不同大小）、业务数据特殊切割索引；
  • Chunk 面试热点：固定长度/结构切 → 讲父子文档（召回精度 vs 上下文完整性矛盾）→ 父子大小怎么定 → 小创新（表格单独建索引、FAQ 按 QA 组织、父子层级按文档结构动态确定）。

检索有创意

  • 多路召回 + 动态：不同路动态权重（召回数量权 + 排序影响力权），按当前步骤/剩余窗口动态调整；
  • Weighted RRF 用于父文档排序（与父子文档 1+1>2）；
  • 迭代式检索（RAG 是核心卖点时的必备）：动态退出条件（按"是否提供新信息"判定，结合 Slot Filling——需确认 A/B/C 三个关键事实，第三轮仍只有 A/B → 边际收益低 → 停止或切换 Query/Retriever）；最小充分检索（每轮先问"最少还需要知道什么"，确定最小目标→检索→判充分→产生下一目标，已具 Agentic 味道）；根据结果动态调整策略（第一轮向量差 → 改 Query/拆问题/增关键字权重/扩 TopK/换数据源/针对缺口构造 Query；Observation 不只告诉"搜到了什么"更告诉"还缺什么"）；必须有 Budget（效果条件：最小充分证据；成本条件：继续检索不值得）——别强调"检索三次"，要强调退出机制设计。

评估有闭环

  • 卖点不是"用了什么指标"（Recall@K/Precision@K/MRR/NDCG/LLM-as-Judge 大家都一样），而是数据驱动迭代：固定测试集，每次调 Chunk/召回路数/TopK/RRF 权重/Rerank/迭代策略都重跑对比，指标下降就把 Bad Case 归因到具体环节（查询改写/Chunk/召回/融合/Rerank）→ 修改 → 回归 → 对比 → 继续迭代；
  • 自定义指标（编辑距离变种）证明会设计指标。

总结：入库有创新，检索有创意，评估有闭环——三合一才是完整有竞争力的 RAG 面试方案。
