评估、反馈与可观测性

一、怎么知道用户喜不喜欢你的 Agent

面试要点：针对每个环节都要准备评测机制，目前面试常考；没有评测方案容易被认为"玩具项目"。

基础评估机制（组合使用，没有万能方法）

机制说明优点缺点
测试集准备一批用例，每次改 Prompt/模型/RAG/流程后重跑稳定、可重复、适合版本对比自造用例难覆盖真实输入
LLM as Judge再调一个大模型按正确性/完整性/约束满足度打分便宜（批量/mini/flash/低峰）、可大规模自动化仍需花钱，无绝对标准
专家评审法律找律师、金融找从业者质量高、可校准 Judge、撰写业务规则贵、慢，只能抽样
用户显式反馈点赞/点踩/评分/满意不满意真实用户亲口说的反馈率极低（不满意直接关页面）
用户隐式反馈重新生成、反复改问题、"不是这个意思"、是否执行建议、是否完成任务数据量大行为含义难解释（聊 10 轮是好聊还是没解决）
A/B Test线上分流两个版本对比任务完成率/纠正率/转化率/留存真实用户判断需流量与灰度机制；可扩展为多臂老虎机
Pairwise 对比同时给 A/B 结果选哪个更好比打分更容易判断真人或 LLM Judge 均可

合理组合：测试集负责稳定回归 + LLM as Judge 负责语义化评估 + 专家负责校准 + 用户反馈与 A/B Test 验证线上真实效果。

测试集三来源：手写（早期）→ AI 生成（参考已有用例，可加人工监督）→ 线上案例回流（自动回流：设计全自动回流流程；手工回流：抽样/告警后人工整理）——面试好用。

业务指标设计（核心方法论）

不要从"我能采集什么数据"出发，而要从"用户为什么使用我的 Agent"反推指标。 用户体验指标 = 通过用户行为揣测用户心理。

三个问题：① 用户为什么来用你的 Agent？② 觉得好用时会做什么？③ 觉得蠢时会做什么？（负向行为：重新输入、修改表达……负向指标往往更有价值——用户懒得点赞，但被惹毛会用行为告诉你。）

电商正向链路：点击率 → 详情页停留时间 → 收藏率 → 加购率 → 下单转化率（偷懒就只看最终下单率——真金白银最靠谱）。但 Agent 可能靠推荐便宜货/爆款/高佣金商品刷转化 → 必须加护栏指标（退货率、退款率）。

三组指标（避免被单一指标骗）：

  • 目标指标：反映用户最终目标（下单转化率）；
  • 过程指标：用户正在朝目标前进（点击率、加购率）；
  • 护栏指标：防止优化带偏系统（退货率、用户纠正率）。
  • 好的优化 = 目标指标提升 + 护栏指标不恶化。例：下单转化率 +8%、退货率持平、用户纠正率 -12%——比"满意度提高 10%"可信得多。

指标必须结合业务解释：

  • 客服 Agent：对话轮数越低越好（20 轮 = 20 轮没解决）；社交 Agent：轮数/会话时长/继续回复率/次日再次发起比例越高越好；教育 Agent：看后续相似题正确率、提示次数、独立完成率、知识点掌握率（直接给答案用户很爽但没学会，甚至"当下觉得麻烦"反而是好事）。
  • 同一指标在不同业务方向可能完全相反。

总结：先确定用户真正想达到的目标 → 寻找达成目标时的行为 → 同时设计负向与护栏指标防止被刷歪。

线上反馈回流：让 Agent 持续演进

什么值得回流（优先强负反馈/异常）：用户点踩、要求重新生成、"不是这个意思/你理解错了"、同一问题反复修改追问、Agent 多次 Replan、工具连续失败、任务失败/中断、LLM Judge 低分、核心指标异常；甚至主动按指标找异常（平均 3-4 轮结束的推荐突然平均 15 轮，抽出来分析）。

回流价值：同一个坑只踩一次（例：用户说不要苹果还推 iPhone → 保存整轮（输入/Context/工具调用/输出/反馈）→ 排查发现"不要苹果"硬约束在上下文压缩时丢失 → 修复 Context 管理 + 把 Case 加入测试集，以后每次改动重跑）。

Evaluation Agent / Optimization Agent（高级，谨慎）：主 Agent 干活，评估子 Agent 周期读取指标（用户纠正率、点赞点踩、Task Success Rate、Judge 分数、Replan 次数、工具失败率、转化率、新增 Bad Case）→ 自动分析异常 → 抽取会话找共同特点 → 自动归因 → 甚至生成新 Prompt（进入评估流程，不直接替换线上）。

两道保险（自动演进必须保留）：① Guardrail Metrics：核心指标提升同时其它关键指标不能恶化；② 人工审批：System Prompt、工具权限、安全策略、资金操作等高风险变更不允许全自动修改。实践中多为"部分自动化 + 人工决策"，面试讲清思想即可加分。

二、Agent 可观测性

核心命题

系统正常运行，不代表 Agent 正确运行。 HTTP 200、大模型调用成功、检索成功、数据库正常、Trace 无异常——但推荐了 9999 元游戏本而用户预算 8000。Agent 可观测性除了回答"系统有没有挂"，还必须回答：Agent 当时看到了什么？为什么这么决定？从哪一步开始错了？

传统三件套依然成立：Metrics（系统整体怎么样：QPS/RT/错误率）→ Trace（一次请求经历了什么：网关→订单→商品→Redis→MySQL）→ Log（某节点具体发生了什么：SQL 没走索引）。Agent 的 Trace 差异：传统 Trace 记录调用链路（经过哪些系统组件），Agent Trace 还要记录决策链路（经历了哪些决策节点）。

记录什么（Agent 核心信息）

至少能回答：用户输入被理解成了什么；Intent/Slot/硬约束；这一轮注入了哪些 Context；当前 Plan 与执行到哪一步；为什么选这个 Tool；Tool 参数与返回；如何处理 Observation；有无 Retry/Replan/Rollback；最终答案。

Context 是排查关键（大模型决策高度依赖当时窗口里有什么）：预算 8000 的例子，逐环检查——用户输入有没有 8000？Slot Filling 提取 budget_max=8000？Context 保留了 8000？思考时带上 8000？推荐 Action 参数 price_max=8000？Tool 结果是否超 8000？任一环节出错结果就错。

核心信息类别：输入与理解结果、Context、决策、Tool 调用、Observation/Evidence、状态变化、最终输出。不要全量永久保存（数据量大 + 隐私安全）：完整 Prompt/Context/Tool Result 只针对抽样请求、异常请求或短期保存。

Agent 特有 Metrics

在传统 RED（Rate/Error/Duration）之外增加：Tool 调用失败率、Retry/Replan 比例、平均 ReAct 循环次数、检索空结果比例、用户纠正率、约束违反率、最终任务成功率。

排查方法

  1. Checkpoint 检查（与 Replan 回溯同构，方向相反：Replan 是 Agent 自己判断回退，可观测性是工程师人工排查）：不从头翻，先查几个 Checkpoint——遇到第一个毫无问题的 Checkpoint，错误就在上一个有问题 Checkpoint 与它之间。Checkpoint 是事后排查的可信锚点（保存任务状态、关键 Context、中间产物、约束满足、Evidence、Check Result）；如果 Checkpoint 只记 step_success=true 则对定位没帮助。
  2. 二分法：Checkpoint 太密成本高、太稀区间大，所以不断选择"最容易出错/最有价值的中间节点"判断错误在前在后缩小范围——优先检查：前科累累的节点、关键节点（Context 明显变化、关键中间结果、切换执行路径、调用外部工具、发生 Replan、修改关键状态）、直觉可疑的节点。范围缩到三五个步骤后自后向前反向追踪因果链。
  3. 组合拳：Checkpoint 定大区间 → 二分法缩小范围 → 反向追踪因果链，比"打开 Trace 从最后一步往前翻"高效得多。

核心指标清单（按业务挑核心，别全监控）

  • 结果类：任务成功率（难点在定义"成功"，常用 LLM as Judge）、端到端耗时、单任务成本、降级/兜底触发率、人工介入率；
  • 质量类：用户纠正率、约束违反率、无依据结论率（幻觉风险）、证据覆盖率、检索空结果率/命中率、上下文遗漏率/丢失率/利用率、Context Token 使用量；
  • 决策类：意图识别准确率、槽位/约束提取准确率、工具选择准确率、检索命中率；
  • 稳定性类：工具调用成功率/重试率/耗时（分工具统计）、LLM 调用耗时（分节点统计）/错误率、Token 消耗；
  • 循环与计划类：ReAct 平均循环次数、最大循环命中率、重试率、Replan 率/成功率、回滚率、Checkpoint 失败率、Plan 完成率（小心 Agent 声称按计划执行实际没执行）、步骤成功率（按 Step 类型拆分找薄弱环节）。

示例聚焦：RAG Agent → Retrieval Empty Rate、Evidence Coverage Rate；长任务 Agent → Replan Rate、Checkpoint Failure Rate、ReAct Loop Count。

面试关键：讲可观测性一定要准备数据（任务成功率、用户纠正率、Tool 成功率、Replan Rate、平均循环次数及优化前后变化）。没有数据只能证明做了监控，无法证明 Agent 做得怎么样。

三、评测体系建设：从答案质量到任务行为

本节整理自图灵 Agent 评测团队的《Agent评测漫谈 —— 由浅入深讲解Agent评测》open in new window。以下按实践主题归纳；文中的业务案例数据仅代表原文报告的实践结果，不作为通用效果承诺。

1. 评测对象是整个 Agent 系统

评测需要回答两个问题：Agent 做得好不好？具体哪里好、哪里不好，下一轮应该改什么？ 它贯穿研发、上线、回归与优化，不能只凭一次 Demo 或离线榜单判断效果。

传统模型评测主要关注模型能力；Agent 的表现则取决于模型、Prompt、Skill、工具、记忆、状态管理和业务流程的共同作用。因此，更换模型之外的任何一个环节，也可能改变评测结果。

两个 Agent 即使都完成任务，也可能一个稳定高效，另一个反复试错后偶然成功。需要同时评估以下四层：

层次核心问题关注内容
结果事情完成了吗？任务完成情况、输出可用性
过程怎么完成的？规划合理性、执行步骤稳定性
效率代价能接受吗？耗时、Token 消耗、工具调用次数
风险是否造成不该发生的影响？越权、误操作、安全隐患

对应两种互补视角：Response Evaluation 看最终输出，Trajectory Evaluation 看执行轨迹。 可观测性提供输入、上下文、工具调用、中间结果与状态变化等证据，评测再依据这些证据判断质量，为迭代提供方向。

2. 用任务指标连接模型能力与业务价值

模型能力提升，不一定带来业务收益。指标体系需要解释两者之间的关系，而不是分别列出模型分数和业务报表。

可以按以下思路建立关联：

模型能力 → Agent 任务表现 → 业务系统表现 → 最终业务价值。

以原文的 AI 搜索场景为例：Agent 层关注意图理解、检索有效性和结果整合可信度；搜索系统关注召回率、点击率；业务关注 DAU、留存等。需要由熟悉业务流程的人共同梳理这些指标的关系，才能分析业务下滑发生在哪个环节，以及模型升级为什么没有转化为收益。

这与前文的目标、过程、护栏指标互补：前者用于连接不同层级的表现，后者用于约束优化方向。

3. 客观评测与主观评测配合使用

  • 客观评测：优先覆盖高频、结构化、可以用明确规则判断的内容。
  • 主观评测：覆盖开放性、高价值和复杂业务问题，由人工明确质量标准。
  • 自动化评测：在人工标准稳定、机器判断经过校准后，承担规模化执行。

主观评测并不意味着随意打分。真正的难点是让不同评测员对同一条样本给出一致判断，再让机器复现这套判断标准。

4. 先统一人工标准，再对齐机器判断

原文将标准对齐分成两步：

  1. 人人一致：产品、运营、研发和 QA 使用同一套评测规范，通过背靠背独立标注发现分歧，再讨论和修正规则。
  2. 人机一致：用人工评测结果校准机器评测，达到可信的一致性后，再扩大自动化规模。

团队需要有明确的标准负责人，在收集各方意见后处理无法达成共识的问题，避免同一个项目出现多套互不兼容的标准。负责人可以组织团队共同建设规范，并不意味着质量定义永远由个人偏好决定；真实业务中的 Good Case、Bad Case 和用户变化仍要持续修正标准。

机器预标注不等于可信的自动化评测。 如果尚未验证人机一致性，机器标签可以辅助人工，但不宜直接当作可靠的质量结论。

5. 将模糊指标拆成可判断的 Rubric

“回答是否自然”“方案是否专业”过于宽泛，直接打 0～10 分容易产生分歧。原文建议：

  1. 指标下钻：把抽象要求拆成具体、可观察的判断项，即 Rubric。
  2. 尽量二元化：每项用“是 / 否 / 未知”或 1 / 0 / unknown 表达，减少分数尺度差异。
  3. 迭代规则：分析 unknown 的占比及对应样本，检查规则是否模糊或证据不足，再验证单条 Rubric 的人人一致率与人机一致率。

原文以骑手外呼的“口语化”为例，将宽泛评分拆成是否使用特定称谓、口语表达和语气词等具体检查项。这些检查项服务于特定业务，不能直接推广为所有对话的质量标准。

以下结合前文商品推荐场景给出一个落地示例（为本文补充，非原文案例）：

模糊要求可检查的 Rubric需要的证据
理解用户需求是否识别预算上限为 8000 元？用户输入、约束提取结果
推荐符合约束是否存在价格超过 8000 元的推荐商品？推荐清单、商品价格
没有编造事实关键商品参数是否有工具返回或检索证据支持？最终回答、工具结果或检索结果

需为每一项明确“是”代表通过还是失败；证据不足时标记 unknown，不要强行判成通过。二元化是降低单项判断的歧义，并不意味着整个任务只能得到一个简单的 0 或 1。

原文将 85%、90% 作为一致性可信阈值的示例，并报告了部分业务中人机一致率从 62% 提升到 92%、另一个业务达到 99% 的结果。这些数值说明其实践效果；实际验收阈值仍需按场景设定，不能直接照搬。

6. 用真实案例逐步建设评测体系

评测流程可以拆成五个环节：

环节主要工作
采集收集线上或沙箱中的原始任务数据
清洗去重、分类、补充上下文、修复脏数据
评测按统一标准进行人工或 AI 评测
质检检查标准是否稳定、判断结果是否可信
分析与归因定位问题，形成优化建议和回归任务

再把这些环节与线上 A/B Test、持续观测连起来，形成迭代闭环。起步时不必设计庞大的指标体系，更实际的路径是：

选择高频核心场景 → 定义少量关键指标 → 收集 Good/Bad Case → 转成标准评测样本 → 优化 Prompt、Skill、策略或模型 → 回归验证 → 从线上继续抽样。

  • Bad Case 暴露能力边界和系统短板，是定位问题、扩充回归集的重要来源。
  • Good Case 定义高质量完成的样子，帮助团队统一“好”的标准。
  • 用户从尝鲜人群扩展到更广泛群体时，需求与预期会变化，评测目标也应随之调整。

冷启动建议先由人工生产少量样本，再由 AI 辅助生成或扩写。是否可以直接小流量上线收集样本，需要权衡业务容错率、构建种子集的成本和线上试错的代价；种子集的作用是先确认基本能力，后续再持续补充边界案例。

7. 行业专家既定义标准，也补充业务知识

在垂直领域，公开语料可能不足以覆盖业务知识。专家参与不仅是给结果评分，还能帮助定义任务要求、优质完成方式和业务规则，尤其适用于冷启动阶段。

当专家意见不一致时：

  • 先提取共同认可的要求，形成基础评测标准。
  • 对存在多种合理做法的部分，区分不同风格或策略，在相应测试集中分别评估。

例如不同销售专家可能偏好不同沟通策略，只要都能满足业务要求，就不应把其中一种合理路径简单判错。评测标准需要约束质量，但不应把所有成功方式限制成唯一执行路径。

四、长程 Agent 与 Skill 的评测

1. 从问答样本转向任务样本

短程问答常围绕 (query, ground_truth, answer) 判断回答质量。长程 Agent 需要分解任务、调用 Tool 或 Skill、读取中间结果并调整策略，更适合按以下三元组组织评测：

(prompt, expected_behavior, trace)
  • prompt：用户的问题或任务诉求。
  • expected_behavior：预期行为与成功标准。
  • trace：Agent 实际执行的完整轨迹。

核心变化是从“回答得怎么样”扩展为“事情是否完成，以及如何完成”。预期行为可以允许多种合理路径，不必要求执行轨迹与某条标准轨迹逐步相同。

2. 区分任务、试验、轨迹与真实结果

概念含义实践作用
Task有明确输入和成功标准的单个测试任务定义测什么、怎样算成功
Trial对同一任务的一次执行尝试用多次执行观察模型随机性造成的波动
Grader检查某方面表现的评分逻辑，可包含多个检查项一个任务可同时评估多个方面
Transcript / Trace / Trajectory一次试验的完整执行记录分析输出、工具调用、中间结果和交互过程
Outcome执行结束后环境的实际状态验证任务是否真的完成
Evaluation Harness执行任务、记录过程、评分和汇总结果的评测基础设施支撑端到端自动评测
Agent Harness处理输入、编排工具、管理执行并返回结果的 Agent 运行系统与模型共同构成被评测对象
Evaluation Suite面向某类能力或行为的一组任务组织覆盖范围与回归验证

Agent 声称成功，不代表环境中的任务已经完成。 原文以航班预订为例：最终回复“已预订”只是一条输出，数据库中是否实际存在预订记录才是结果证据。因此，评测既要读取 Trace，也要核对环境的最终状态。

3. Skill 评测要进入开发与发布流程

Skill 的创建门槛降低后，需要评测的人会从少量专业人员扩展到更多业务角色。评测工具应简单、标准化、自动化，并便于接入开发和发布流程。

长程任务的轨迹更长、信息更密集，Skill 数量也会增加，完全依靠人工逐条阅读难以扩展。原文提出，流程可以从“核心评测员对齐 → 外包对齐 → 机评对齐”，缩短为“核心评测员对齐 → 机评对齐 → 规模化扩展”。相应分工为：

  • 人工：设计高价值标准、对齐 Rubric、处理分歧。
  • AI：执行规模化评测、初筛与回归验证。
  • 平台：管理案例、保存和回放轨迹、告警与辅助归因。

这一转变的前提仍是机器评测与人工标准一致；自动化的价值在于扩大统一标准的覆盖范围。

4. 长程 Agent 评测平台的基础能力

能力要解决的问题
全链路回放还原任务从输入到结果的过程，支持定位问题
Case 管理统一维护任务样本、上下文、约束和 Rubric
执行沙箱按只读、可写、高风险等操作类型隔离执行
AI 评测引擎基于 Rubric 完成人机对齐与自动判分，便于 Skill 创建者接入
报告与归因指出问题发生在规划、工具、环境还是 Skill，而不仅给出总分
回归机制版本升级后自动运行历史案例，识别能力退化
准入准出门禁把评测结果接入开发、发布和运营流程

与前文结合，完整落地链路是：记录任务与执行证据 → 按统一规则评测 → 归因并修复 → 历史案例回归 → 线上验证 → 新案例回流。
