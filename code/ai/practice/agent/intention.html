意图识别（Intention Recognition）

一、用户输入规范化

用户输入随意（病句、倒装、代词、缩写、黑话），用户输入规范化 = 理解并修正输入。重要性 ≈ 传统软件工程中的需求分析；能主动谈"处理奇特用户输入"是面试差异化优势。

常见输入问题（六类）

大类说明典型例子
指代问题"这个/那个/第一个/刚才那个""第二个适合生产吗？"
缺失问题缺主语/宾语/动作对象/约束"市场占有率多少？"（实指某公司）
表达问题口语化、病句、临时改口"不是，我说的是另一个"
词义问题非标准术语、黑话、多义词"RAG / 检索增强 / 知识库"
主观判断问题依赖个人偏好与标准"哪个最有性价比？再高级一点"
外部事实问题需实时数据/工具返回"最近哪个框架最火？"

处理时机（两阶段）

  1. 意图识别之前（推荐：通用/C 端 Agent 独立做）；2. 与意图识别一起（领域专属 Agent）；3. ReAct 循环中（深度处理，如"性价比"类形容词只能在此阶段）。

→ 初步处理（大部分输入）+ 深度处理（依赖上下文/工具调用，嵌入 ReAct 循环）。

Prompt 要点

  • 职责边界：能指代消解/省略补全/病句修正/术语标准化/黑话解释/多义词消歧/判断是否澄清或搜索；不能直接回答、执行工具、做最终推荐、判断业务意图、生成完整方案、擅自补充事实、强猜低置信内容、伪造实时信息。
  • few-shot：覆盖各类输入；线上遇到怪输入再沉淀；示例多时用检索注入最相关案例。
  • 完整性检查：主谓宾完整、代词完全消解（输出代词消解表格并作为关键事实贯穿对话）、形容词"可量化"。
  • 命名：输出"TCC 方案"而非"方案一"，用户后续可按名索引，规避模型引用错误；推断不出时引入澄清机制。

进阶：深度整合上下文（核心结论）

  • 结合用户画像、关键事实、对话历史召回。
  • 属性 + 检索推理（时间跨度大 + 属性指代）：先用属性（"樱花、旅游"）检索历史对话细节入窗，再让大模型推断消解；失败补偿 = 提取属性作为参数发起工具调用。
  • 行业画像 + 自演进词汇表：维护词汇表（MySQL/向量库），处理前先检索注入；沉淀多人对话中的高频特殊词汇 → 公共词汇表 + 个人词汇表；阈值话术：总次数 > 100 / 讨论人数 > 3 / 连续讨论 10 次。
  • 可量化：形容词转工具参数（"性价比"→ 同等价格下质量更好；价格参数限定 [150, 200]）；判定方式写进 Prompt/Spec。
  • 未解决问题（参考）：反话/嘲讽、数量范围歧义（"草拟一个题目"→ 要一组）、复杂人物关系指代。

二、三层意图识别机制

意图识别 = intent classification（选业务流程）+ Slot Filling（抽参数）。面试别答"调一次大模型判断"。

时机与必要性

  • 三种时机：与规范化混合 / 循环前独立（面试推荐：边界清晰可评估）/ 循环内。
  • 为什么要独立做：① 决定 Prompt/Spec 加载（售前 vs 售后完全不同）；② 决定上下文组织（避免浪费窗口）；③ 决定工具选择与子 Agent 分发。
  • 金句："意图识别不是为了贴标签，而是决定 Agent 怎么想、加载什么上下文、调用什么工具、进入哪个业务流程。"

Prompt 写法

  1. 候选意图封闭集合（不允许模型发明意图，代码校验兜底）；
  2. 定义相近意图边界（推荐/比较/查询的区分）；
  3. 定义 Slot：category、budget、usage_scenario、brand、must_have_features、nice_to_have_features、hard_constraints、soft_preferences；
  4. few-shot 覆盖易混淆边界。

识别不出的两个出口

  • unsupported → 拒识；unclear → 澄清（missing_slots + clarification_question）。
  • 观点：先收齐参数再回答，好的回答比快的回答体验更好。

三层机制（核心）

  1. 代码层（页面引导/关键字/正则/规则引擎）：快、准、便宜、稳定；
  2. 轻量级大模型（Flash/Mini）：快和省，处理无需深度推理的输入；
  3. 深度推理大模型：复杂表达、强依赖上下文、意图切换、多意图、隐含补全。

流程：第一层 → 第二层 → 第三层。为什么不能跳过第二层：大多数输入明确，轻量模型又快又准。原则：效果 > 效率。

置信度分级：> 0.85 接受；0.6–0.85 仲裁/澄清；< 0.6 交第三层。confidence 非真概率，需结合规则命中/向量相似度/历史准确率。

Slot Filling 与约束

  • missing_slots 字段描述缺失参数，循环中补全至为空。
  • 硬约束（必须满足）vs 软约束（努力满足，未满足要告知用户）；约束贯穿整轮对话。

评估指标

  • Top1 / Top-K Accuracy（实践基本看 Top1）；
  • 分意图准确率（防高频意图掩盖低频重要意图）；
  • 拒识准确率、误拒率、漏拒率、澄清触发准确率、澄清后收敛率；
  • 槽位准确率/召回率/必填槽位完整率/更新准确率、约束识别准确率（普遍最差）；
  • 跨轮反馈：用户"你理解错了"是上一轮意图识别失败的信号，下一轮先评估上一轮效果。

准确率参考：专属领域 99%+；通用 Top1 80%–90%（水分大）。面试要为"太高/太低"各备解释；用测试集实测出数。

测试集覆盖：标准表达、口语化（结合规范化）、槽位缺失、拒识、易混淆；进阶：跨轮补充、约束、意图切换、多意图。

三、提高准确率：五类问题与解法

不准的原因

  1. 意图太多（窗口放不下、选择准确率下降）；2. 边界重叠不正交；3. 口语化严重；4. 一句话多个意图；5. 多轮时间线问题（补充/修改/取消/切换/恢复）。

解法（面试挑 2–3 个讲即可）

  1. 层次意图（决策树式，一级/二级…）：结合迭代式识别与 Slot Filling，结构清晰准确率高；缺点性能差。
  2. 结合检索缩小候选集：先检索候选意图再让大模型筛选，N 可动态（窗口空闲 N 大、重试时 N 更大）；或两级大模型（轻量粗筛 + 深度终审）——"动态上下文"的体现。
  3. 动态 few-shot：固定部分（unclear/unsupported 等通用规则）+ 可变部分（检索注入最相关案例），减少无关干扰。
  4. 保证意图正交：重叠就拆分新意图；或合并相似意图 + 参数区分（用代码/工具处理模型易错点）；差异建模成参数而非意图。
  5. 多意图：先判"是否真的多意图"（过滤过程性描述，如"查询数据并导出 Excel"本质是导出）；输出 {intents, relations} 描述依赖（src/dst/constraints）；Plan 阶段解析依赖安排顺序。建议：不支持多意图，一次只做一件事并询问是否继续——交互感强 + 降本。
  6. 向量匹配兜底：把"用户输入-向量"对绑定意图，纯内存检索，性能极好；离线分析多轮对话沉淀反馈闭环。面试推荐方案。
  7. 不识别，后回滚：默认复用上一轮意图，发现不对回退重识别（"奇诡"差异化做法）。
  8. 多识别器仲裁：多个识别器（向量/大模型/规则）投票或加权计分（权重 × 置信度）；理论意义大于实践。
  9. 微调：双刃剑，面试一般不主动用。

面试建议：向量化方案 + 意图正交 + 不识别后回滚（差异化亮点）。

四、意图识别面试攻略

简历写法

  • 个人技能/优势：融入"Agent 工程化"能力线（体量太小不单列）；点技术关键字（分层意图识别、Slot Filling）+ 提及"优化意图识别准确率"（引导面试官追问）。
  • 项目贡献：模板 基于 A，结合 B，并通过 C，提升/优化/完善了 D、E、F 等效果；A 是方案基石（技术方案、水平不差、面试官能望文生义）；最终数据绝对值 + 相对值双管齐下；写数字就要能解释（怎么统计、太高/太低、是否了解业界水平）。

示例："基于分层意图识别与 Intent + Slot Filling 机制，结合动态 few-shot 和向量兜底，并通过拒识澄清、槽位补全、多识别器仲裁和反馈闭环，将核心意图 Top1 准确率提升至 xx%，较优化前提升 xx%，平均识别耗时控制在 xx ms 以内。"

竞争力方案（v0 → v1 → v2）

  • v0：只有一次深度推理调用，无输入规范、无效率考虑、无数据支撑、边缘情况多（备几个"脑洞大开"的用户输入）。
  • v1 分阶段：① 引入轻量级大模型；② 引入代码层/向量（快速判定 + 兜底怪输入）；③ 高级机制（显式输入规范、动态 few-shot、层次意图/检索过滤、反馈沉淀、多意图（谨慎）、微调（防追问））。
  • v2（未来）：反话处理（部分领域）、离线/在线分析（N+1 轮评估第 N 轮效果）。

实践建议：先评估现有 Agent 的意图识别效果，建立长期成败监控机制。

提高意图识别准确率的方法

Slot filling

通过对不同的意图建立结构化的槽位，思路就是仔细告诉大模型需要识别哪些参数，并且要对识别之后的参数进行检查。例如说用户输入“帮我推荐一台笔记本，主要是写代码，最好轻一点”。

系统应该输出的是：

{
  "intent": "product_recommendation",
  "slots": {
      "category": "笔记本电脑",
      "usage_scenario": "写代码",
      "soft_preferences": ["轻一点"] },
      "missing_slots": ["budget_max"],
      "need_clarification": false 
	}
}

其中有一个字段 missing_slots 也就是描述用户的输入是缺少了有关预算的参数。

missing_slots 这个字段涉及到了 Slot Filling 的高级做法：结合上下文，在 ReAct/TAO 循环中补全所有的槽位，确保 missing_slots 为空，如图：

层次意图

层次意图的基本理念是将意图按照菜单那样来组织，分为一级意图、二级意图等。

这种机制可以和 Slot filling 混合使用，最终达成的效果就非常接近 ReAct/TAO 的范式

结合检索的意图识别

适合系统意图很多的情况，并且原始积累了大量的用户输入数据，具体做法是在意图识别之前先加一个检索的步骤，而后只把有可能的意图传递给大模型，让它进一步筛选。

同时检索可以比较好的识别一些用户输入的行业黑话，通过对用户的行业黑话进行向量打标

意图非常多的时候也可以使用一个轻量的大模型先做一个筛选，不一定要使用检索

动态 few-shot

few-shot 的做法是将样例放入提示词中，如果全部放进去，Prompt 会变得很长，如果只放几个固定示例，又可能和当前用户输入关系不大，这个时候我们会考虑动态 few-shot。

相应的解决方案是将 few-shot 案例全部放入到数据库中（可以是普通的数据库，也可以是 Elasticsearc，还可以是向量数据库），在拼接提示词的时候，先去检索一些相关性最强的 few-shot。

从理论上来说，few-shot 应该包含两个部分：不变的部分和可变的部分，不变的部分主要是针对一些特别的场景，要求大模型无论在何种场景下都要考虑进去。如 unclear 怎么处理，unsupported 怎么处理……可变的部分是跟当前用户的输入、上下文相关性比较强的 few-shot，整个提示词的 few-shot 部分的模板大概长这样：

# few-shot
固定的 few-shot 直接在 Prompt 里面写死
## few-shot 1 xxx
--动态的few-shot案例，结合搜索注入--
{{ .DynamicFewShots }}

保证意图正交

意图正交说的是要确保不同的意图之间的功能和职责是相互独立的，避免彼此之间有重叠或冲突。

  1. 拆分一个新的意图

  2. 将相似度高的意图合并为一个，进一步要求大模型识别出来一些参数，而后自己写一个工具，根据参数识别准确的意图

意图识别评测

意图识别主要对以下关键指标进行评测：

  1. Top-K Accuracy：意图识别K个候选项正确答案的比例。
  2. 拒识准确率：应该拒识的时候，系统是否拒识。
  3. 误拒率：本来能处理，却被系统错误拒识。
  4. 漏拒率：本来应该拒识，却被系统强行归类。
  5. 澄清触发准确率：缺少关键信息时，是否正确追问。
  6. 澄清后收敛率：追问之后，用户任务是否顺利推进。

如果有使用Slot Filling，通常会评测如下指标：

  1. 槽位准确率：抽出来的槽位值是否正确。
  2. 槽位召回率：用户提供的信息有没有被抽出来。
  3. 必填槽位完整率：启动流程必须的槽位是否齐备。
  4. 槽位更新准确率：多轮对话中新信息是否正确覆盖旧信息。
  5. 约束识别准确率：硬约束和软偏好是否识别正确。
