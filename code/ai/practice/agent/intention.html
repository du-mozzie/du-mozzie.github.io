意图识别（Intention Recognition）

意图识别可以拆成两个部分：Intent Classification（选择业务流程）+ Slot Filling（提取流程所需参数）。在此之前，通常还需要对用户输入做规范化，处理指代、省略、口语和行业术语等问题。

它的作用不只是给用户输入贴标签，还会决定 Agent 加载哪些 Prompt/Spec、组织哪些上下文、选择哪些工具，以及进入哪个业务流程。

整体流程可以理解为：输入规范化 → 意图识别与槽位提取 → 校验与澄清 → 业务执行。依赖工具结果或后续对话的信息，可以在 ReAct/TAO 循环中继续补充。

一、用户输入规范化

用户输入往往包含病句、倒装、代词、缩写或黑话。规范化的目标是在保留原意的前提下，让输入变得明确、可处理，而不是擅自替用户补充需求。

1. 常见输入问题

大类说明典型例子
指代问题“这个、那个、第一个、刚才那个”指向不明“第二个适合生产吗？”
缺失问题缺主语、宾语、动作对象或约束“市场占有率多少？”（缺少公司名称）
表达问题口语化、病句、临时改口“不是，我说的是另一个”
词义问题非标准术语、黑话、多义词“RAG / 检索增强 / 知识库”的使用边界不清
主观判断问题依赖个人偏好与评价标准“哪个最有性价比？再高级一点”
外部事实问题需要实时数据或工具返回结果“最近哪个框架最火？”

2. 处理时机与职责边界

可以分成两个阶段：

  • 初步处理：在意图识别前独立执行，或与意图识别合并执行。通用 Agent 可以独立设置规范化模块；领域专属 Agent 可以结合业务一起处理。
  • 深度处理：在 ReAct/TAO 循环中，结合历史上下文、工具结果和用户反馈，进一步解决歧义。

如果规范化是独立模块，Prompt 应明确它的职责：

  • 可以做指代消解、省略补全、病句修正、术语标准化、黑话解释和多义词消歧，并标记是否需要澄清或查询外部信息。
  • 不直接回答业务问题、调用工具、做最终推荐或生成完整方案；不擅自补充事实，不强猜低置信内容，不伪造实时信息。
  • 业务意图分类由后续模块负责；若采用合并方案，则需要在输出结构中区分规范化结果与意图识别结果。

3. Prompt 与上下文设计

完整性检查：检查动作、对象和必要约束是否明确，代词是否能可靠消解。可以输出“代词—实体”映射，并将其作为关键事实保留在后续上下文中；无法确认时进入澄清流程。

稳定命名：使用“TCC 方案”等明确名称，少用“方案一”“刚才那个”。用户后续可以按名称引用，降低跨轮引用错误。

few-shot 覆盖：覆盖不同类型的输入问题，将线上遇到的特殊表达沉淀为案例；案例较多时，检索注入最相关的示例。

深度整合上下文：结合用户画像、关键事实和历史对话召回。例如用户通过“樱花、旅游”等属性指代很久之前讨论的地点，可以先检索历史细节，再让模型消解指代；信息不足时继续查询或澄清。

行业词汇表：维护公共词汇表和个人词汇表，处理输入前先检索注入。高频特殊词汇可以进入候选词汇表，但是否收录仍需校验，避免把个人用法误当作通用术语。

主观描述具体化：把“性价比高”“轻一点”等描述转成可比较的标准或工具参数。例如先确认预算范围，再比较同价位产品的质量、重量等指标。不能仅凭“性价比”自行推断出 [150, 200] 这样的价格范围。

反话、嘲讽、数量范围歧义和复杂人物关系指代，可以作为后续测试与优化的重点。

二、意图识别与槽位提取

1. 为什么需要独立识别意图

意图识别可以与规范化合并，也可以放在 Agent 循环前或循环内。将其作为独立模块的好处是边界清晰、便于评估，并能提前决定：

  • Prompt/Spec 加载：例如售前咨询和售后处理使用不同的业务规则。
  • 上下文组织：只加载当前任务需要的信息，减少无关内容占用窗口。
  • 工具与子 Agent 分发：将请求交给对应的业务流程。

2. Prompt 设计要点

  1. 限定候选意图集合：不允许模型随意发明意图，输出后通过代码校验。
  2. 说明相近意图的边界：例如推荐、比较和查询分别适用于什么场景。
  3. 定义每个意图的槽位：明确类型、是否必填、取值范围和校验规则。
  4. 提供边界示例：few-shot 应覆盖容易混淆、无法处理和信息不足的输入。

以商品推荐为例，槽位可以包括 category、budget_max、usage_scenario、brand、must_have_features、nice_to_have_features、hard_constraints 和 soft_preferences。实际使用时应按业务需要裁剪。

3. Slot Filling 示例

用户输入：“帮我推荐一台笔记本，主要是写代码，最好轻一点。”

假设该推荐流程要求先确认预算，结构化结果可以是：

{
  "intent": "product_recommendation",
  "slots": {
    "category": "笔记本电脑",
    "usage_scenario": "写代码",
    "soft_preferences": ["轻一点"]
  },
  "missing_slots": ["budget_max"],
  "need_clarification": true,
  "clarification_question": "你的预算上限是多少？"
}

missing_slots 用来记录当前流程缺失的必填参数。系统可以结合已有上下文、用户补充和工具结果逐步填充，启动对应业务动作前再校验是否齐备。可选参数不必全部收齐，也不应为了清空字段而编造值。

槽位还需要区分两类约束：

  • 硬约束：必须满足，例如预算上限、必须支持的功能。
  • 软偏好：尽量满足，例如更轻、更安静；无法满足时说明取舍。

约束应贯穿当前任务。多轮对话中，用户可能补充、修改或取消条件，需要正确更新已有槽位。

4. 无法直接推进时的出口

  • unsupported → 拒识：请求超出系统支持范围，说明能力边界。
  • unclear → 澄清：无法确定用户想做什么，询问区分候选意图的关键信息。
  • 意图明确但必填槽位缺失 → 补参：保留已识别的意图，通过 missing_slots 和 clarification_question 收集必要信息。

澄清应服务于任务推进，优先询问会影响结果或执行安全的关键信息，避免对无关的可选参数反复追问。

三、三层识别机制

可以按请求复杂度设计分层识别流程：

层级实现方式适用场景
代码层页面入口、关键词、正则、规则引擎明确、稳定、可用规则覆盖的输入
轻量模型层Flash/Mini 等轻量模型规则未覆盖，但无需复杂推理的表达
深度推理层推理能力更强的模型强依赖上下文、复杂表达、意图切换或多意图

通常从代码层开始，无法可靠判断时再升级。分层的目的是平衡效果、耗时和成本，不要求每个请求都依次调用全部三层。

可以设置置信度区间，分别用于接受、仲裁或澄清、升级处理。例如 > 0.85 接受、0.6–0.85 仲裁、< 0.6 升级，只能作为待验证的初始配置。

模型输出的 confidence 不是真实正确率。阈值应结合规则命中情况、向量相似度和验证集表现校准；进入最后一层后仍无法确定的请求，应拒识或澄清。

四、提高意图识别准确率

常见问题包括：候选意图过多、边界重叠、用户表达口语化、一句话包含多个任务，以及多轮对话中的补充、修改、取消、切换和恢复。

1. 层次意图

像菜单一样组织一级、二级意图，先判断大类，再识别具体业务。

层次意图可以与 Slot Filling 结合，在逐步缩小意图范围的同时补充参数，形成接近 ReAct/TAO 的迭代流程。

这种方式能减少单次判断的候选范围，但会增加调用次数和延迟，上层误判也可能影响后续分支。

2. 结合检索缩小候选集

意图很多、历史输入积累较多时，可以先检索相关意图或历史案例，再将候选项交给模型筛选。已标注的行业黑话案例也可以帮助召回对应意图。

候选数量可以根据上下文预算和重试情况动态调整。需要关注候选召回率：正确意图没有被召回时，后续模型很难选对，应允许扩大范围或进入澄清流程。

也可以使用轻量模型先粗筛，再由推理能力更强的模型精判。

3. 动态 few-shot

全部案例都放进 Prompt 会增加长度和干扰；只放固定案例，又可能与当前输入无关。

可以将案例存入普通数据库、Elasticsearch 或向量数据库，在构造 Prompt 时检索最相关的案例。few-shot 分成两部分：

  • 固定部分：覆盖 unclear、unsupported 等通用边界。
  • 动态部分：结合当前输入和上下文，注入相关案例。
# few-shot
## 固定案例
说明 unclear、unsupported 等通用场景的处理方式。

## 动态案例
{{ .DynamicFewShots }}

4. 保证意图边界清晰

意图正交强调不同意图的职责尽量独立，避免同一输入同时符合多个互斥标签。

如果重叠部分确实对应独立业务，可以拆出新意图，同时重新定义原有意图的边界。

如果差异只是参数不同，可以合并相似意图，由模型提取参数，再通过代码或工具分发到具体流程。

核心原则是：能建模为参数的差异，不必都拆成新意图。

5. 多意图与多轮状态

先区分“多个独立目标”和“完成一个目标所需的多个步骤”。例如“查询数据并导出 Excel”在某些业务中可以建模为一个导出流程，而不是两个独立意图。

如果支持多意图，可以输出 {intents, relations}，描述任务之间的依赖和约束，再由规划阶段安排执行顺序。如果产品只支持单任务，应说明限制，让用户选择优先处理的任务。

多轮对话还需要判断当前输入是在补充、修改、取消、切换还是恢复任务。对于连续补参场景，可以复用上一轮意图；发现切换信号或参数不匹配时，再重新识别。所谓“先复用、后回退”应发生在识别与规划阶段，不能依赖事后回滚已经产生外部影响的业务动作。

6. 其他优化手段

  • 向量匹配：将已标注的用户表达与意图绑定，用于快速匹配或辅助判断；可对小规模数据使用内存检索。通过离线分析多轮对话，持续沉淀案例。
  • 多识别器仲裁：结合规则、向量和模型结果进行投票或加权，但要处理分数不可直接比较、错误相关和额外延迟等问题。
  • 微调：在标签体系稳定、标注数据充足且评估表明确有收益时考虑，同时评估维护成本。

五、评估与反馈闭环

1. 意图识别指标

指标关注点
Top1 Accuracy第一候选意图是否正确
Top-K Accuracy前 K 个候选中是否包含正确意图
分意图指标各类意图的表现，避免高频类别掩盖低频重要类别
拒识召回率应该拒识的请求中，有多少被正确拒识
误拒率可处理请求中，有多少被错误拒识
漏拒率应拒识请求中，有多少被错误归入支持的意图
澄清触发准确性是否在需要澄清时追问，是否存在不必要的追问
澄清后收敛率追问后，任务能否在约定轮数内推进

评估前要约定样本范围、计算分母和成功标准，尤其避免用一个含糊的“拒识准确率”混淆不同指标。

2. 槽位与约束指标

  • 槽位准确率：抽出的槽位值是否正确。
  • 槽位召回率：用户提供的槽位信息是否被完整提取。
  • 必填槽位完整率：启动流程所需的必填参数是否齐备。
  • 槽位更新准确率：多轮对话中的新信息是否正确覆盖或撤销旧信息。
  • 约束识别准确率：是否正确区分硬约束与软偏好。

同时记录识别耗时、模型调用次数和成本，评估分层方案的实际收益。

3. 测试集与跨轮反馈

基础测试集应覆盖标准表达、口语化、槽位缺失、拒识和易混淆意图；进一步覆盖跨轮补充、约束修改、意图切换、多意图和异常表达。

用户下一轮说“你理解错了”，可以作为上一轮识别失败的候选信号，但仍需区分意图识别、槽位提取和业务执行等具体原因。经过复核的案例，再用于补充规则、词汇表和动态 few-shot。

准确率应由测试集实测得出，并同时说明领域范围、类别分布和统计口径，不直接把未经验证的行业数字作为目标或结论。

六、面试与项目表达

1. 简历写法

意图识别可以融入“Agent 工程化”能力线，突出分层识别、Slot Filling、动态 few-shot 和评估闭环。在项目贡献中，说明方案、解决的问题和验证结果。

示例模板（仅填写实际做过的机制和测量数据）：

基于分层意图识别与 Slot Filling，结合动态 few-shot 和向量匹配，通过拒识澄清、槽位补全及反馈闭环，将核心意图 Top1 准确率由 xx% 提升至 yy%，平均识别耗时控制在 zz ms 以内。

写出数据后，要能解释测试集来源、统计口径、优化前后的可比性，以及准确率与延迟、成本之间的取舍。注意区分“提升了多少个百分点”和“相对提升了百分之多少”。

2. 按演进过程讲方案

  • v0：建立基线。先用单次模型调用完成识别，收集错误案例，测量准确率、耗时和成本。
  • v1：针对问题优化。根据错误分布，引入输入规范化、代码规则、轻量模型、动态 few-shot、层次意图或检索候选，逐项验证收益。
  • v2：完善长期反馈。分析多轮修正和线上失败案例，持续更新测试集、规则和案例库，再按实际需求考虑多意图或微调。

面试时选择两三个有真实实践支撑的优化点，讲清楚“什么输入会失败、为什么这样改、如何证明有效”，比罗列所有机制更有说服力。
