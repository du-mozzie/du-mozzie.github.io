上下文管理：Context / Context Window

一、Context 统一抽象

核心概念

  • Context = Agent 当前可获得的全部信息空间（仓库）；Context Window = 当前调用真正交给模型的工作集（工作台）。
  • Context Window = f(Context) 揭示了 Agent 工程的核心：找准内容，放进 Context Window，传递给大模型。
  • Memory 只是部分 Context 的别名（拟人化描述，针对大模型无状态）：短期记忆/Session Memory = 与当前多轮对话相关（临时数据 + 长期记忆的缓存）；长期记忆 = 需持久化的记忆。不要被 Memory 概念神化，本质只有 Context。

Context 数据来源四块：用户输入数据（Excel/PDF 等）、Agent 自身产生（Prompt、中间结果）、内部数据（业务系统/MySQL/ES）、外部数据（外部接口/工具/MCP）。

Context 分类（面试八股）

Instruction Context（System Prompt/业务 Spec，限定怎么思考、能做什么不能做什么）、Goal Context（最终目标+子目标，一把标尺）、User Context（用户画像、历史决策，"懂我"关键）、Task Context（当前任务、执行步骤）、Tool Context（工具输入输出）、Constraint Context（硬约束/软约束，运行边界）。

一切问题的根源都在 Context：输入规范化要结合 Context；意图识别产物应包含 Context Requirement；Replan 本质是 Context 变化后的受控修正。Agent = 在 Context 中变化的状态机。

Context Item：统一抽象（可扩展）

{"id":"ctx_001","type":"constraint","content":"不能修改 A 接口","source":"user",
 "scope":"current_task","authority":"high","confidence":1.0,
 "expires_at":null,"priority":100,"token_cost":8,"version":2}
  • source：信息从哪里来；scope：有效范围（步骤/任务/会话/项目/用户/全局，toB 加部门公司、toC 加家庭聊天）；
  • authority 权威度（冲突仲裁用）：系统规则 > 用户明确输入 > 工具事实 > 已确认摘要 > 模型推测；
  • confidence 可信度（小 Agent 可与 authority 二选一）；
  • expires_at：过期时间（用户偏好久、天气短）；token_cost：注入成本（动态组装窗口时用）。
  • 每个 Item 都要想：怎么获得、怎么存储（是否持久化/缓存/数据结构）、怎么查询（细节召回）。

f 的流水线

Window = Inject(Order(Compress(Select(Retrieve(Context)))))：Retrieve 找出可能相关 → Select 选出真正需要 → Compress 压缩到合适粒度 → Order 决定顺序 → Inject 注入大模型。

滑动窗口算法（基础方案）

  • 窗口只保留最近 N 轮对话（按轮次或按 Token 计量）；优点：实现简单、性能稳定、不需要检索、近期最相关、易控成本。
  • 窗口外的内容靠摘要 + 细节召回。摘要时机：每 N 轮生成一次（即时生成 = 第 KN 轮结束立刻生成；延迟生成 = 第 KN+1 轮开始时回头生成）。
  • 轮次窗口追问：限制每轮用户最大输入 X、模型最大输出 Y，N 轮 = N*(X+Y)。
  • 变种：近 N 轮原文 + 近 [N+1, N+M] 轮"用户输入原文、模型输出摘要"（模型输出长、信息密度低）；N/M 可动态调整。
  • 注意：滑动窗口不要占满窗口（128K 窗口只给对话留 32K）；可把关键点、中间产物放进窗口；致命问题：最近的上下文不一定最重要。

分层上下文（高级方案，分而治之）

可按五个角度分层（可混用、可排列组合，结合业务特点选一个即可）：

角度层级示例
生命周期工作（几次调用）→ 会话（当前对话）→ 长期（画像/已确认事实）→ 归档（按需召回）
作用范围步骤级 → 阶段级 → 任务级 → 会话级 → 用户级 → 系统级
信息形态原始层 → 结构化事实层 → 摘要层 → 索引层（只存"去哪里找"）
权威性强规则（不允许被覆盖）→ 已确认事实 → 有证据推断 → 待确认假设（不得当事实）→ 已否定（禁止使用）
冷热程度热（内存/Redis）→ 温（需检索）→ 冷（归档追溯）

关键是层间映射 f1/f2：按规律从下一层挑出上一层内容，多准备几个 f 就是独属于你的分层上下文。

二、动态编排：Context Compiler

抽象

Window_t = Inject(Order(Compress(Select(AllContext_t, TaskState_t), TokenBudget_t)))：结合任务状态与 Token 预算，把全部可用 Context 加工成最终窗口。上下文窗口是 Select→Compress→Order→Inject 的产物。

前置知识：Prompt Prefix Cache（前缀索引思想）——Prompt 前缀相同可复用推理缓存，所以顺序设计要考虑缓存命中。

Select：当前步骤真正需要什么（弱水三千只取一瓢）

三种机制可混用：

  1. 强规则筛选：Prompt 模板占位符（{{ .UserProfile }}）、代码写死调用内容（LLMAction 二次封装/装饰器）；
  2. 检索召回：根据调用目标去向量库/ES/数据库找相关内容（类似 RAG，含查找/过滤/重排）；
  3. 模型筛选：正式调用前先让 flash/mini 快速判断需要什么 Context（成本高、性能差，不常见）。

Compress：压缩到什么程度

原则：越重要越不能压缩（或压缩程度越低）；剩余窗口越大越不需要压缩；同一个内容在不同任务目标下压缩策略不同（商品推荐中画像简单压缩，售后可极度压缩）。为同一信息准备多个精度版本按需加载（L0 一句话摘要 → L1 关键结论 → L2 结构化事实 → L3 详细摘要 → L4 完整原文），运行期零额外压缩开销。

Order：顺序即重要性

大模型对顺序敏感（"炼丹"状态），越重要越靠前。参考排序：System/Spec → 当前 Goal → 硬约束 → 任务状态/Plan 节点 → 已确认关键事实 → 当前步骤 Evidence → 工具 Observation → 候选 Action/Tool → 动态 few-shot → 历史摘要 → 补充背景。同时考虑缓存：改动少的内容（已确认关键事实）前置可提高 Prefix Cache 命中。

高级：按剩余窗口大小动态决策（预算分配问题）

把窗口看成预算池（32K 窗口，系统提示/输出/工具参数占掉后只剩 20K 可用）：

  • 必须原样放（压缩/遗漏会导致严重错误）：最新用户输入、硬约束、已确定关键事实、Plan 及执行状态；
  • 可压缩的：按剩余窗口比例定档（L1 一句话：剩余 (0%,10%)；L2 结构化摘要：[10%,30%)；L3 详细摘要：[30%,50%)；L4 原文：[50%,100%]）；
  • 只放索引 / 完全不放：等模型发现缺失再召回（兜底条款：压缩程度太高可召回更详细内容，需配套召回 Action；窗口满了召回也没用）。

动态压缩档位：Full Mode [80%,100%] 原文直放 → Balanced Mode [20%,80%) 大部分时间运行 → Compact Mode [5%,20%) 短时进入尽快退出 → Minimal Mode [0,5%) 不健康状态需监控。其他可纳入动态策略的因素：当前步骤、任务风险等级（高风险用大窗口模型）、信息可恢复性、信息可信度（用户确认 > 权威工具 > 原始文档 > 历史摘要 > 模型推测）、信息新鲜度（新信息优先，但用户画像类老信息重要性高）、工具调用需求（工具描述压缩慎用，会严重影响选择准确率）、few-shot 动态策略、失败历史（常缺失的 Context 提高优先级）。

动态编排决策表示例：当前用户输入始终原文；Goal 完整→结构化→简化→一句话；硬约束始终完整原样；历史对话详细摘要→结构化摘要→一句话+索引→只放索引；用户画像完整→任务相关→关键画像→默认不放；few-shot 3-5 个→1-2 个→默认不放；工具描述完整→核心描述→名称+边界→名称+一句话。

三、摘要与细节召回

摘要类型（一对双生子）

  • 对话整体摘要：达成一致内容（可入关键事实）、进度/里程碑、用户相关信息；多意图切换时分意图存储；长期保存、不入归档；
  • 对话章节摘要：长对话按章节（每 20 轮或按语义）独立摘要；用法：整体摘要 + 最近 N 个章节摘要（N=2,3），或全章节摘要（细节丰富但占窗口）；
  • 大模型输出摘要：不传原文传摘要，有效节省 token；
  • 关键事实：会影响后续决策/工具调用/上下文组织/最终输出/约束校验的信息。分类：目标类事实（用户改意图）、硬约束、软偏好、用户确认过的事实（正+反）、决策类事实（做了什么+为什么）、实体信息（实体表，量大时 Redis/MySQL + RAG）；
  • 中间结果：反复用到的工具输出也要摘要 + 召回；注意时效性（实时查询只用于当轮）。

什么细节值得召回

判定标准：细节是否影响当前决策——影响目标的细节（简历 vs 架构）、影响约束、影响路径选择（方案 A 已失败）、影响工具调用（工具不可用）、影响最终表达（"简单点说话"）。关键事实提取做得好时，大部分场景不需要召回细节。

摘要生成时机

同步（使用前，如滑动窗口 N%10=0 时、组装窗口放不下时被迫压缩）或异步（第 N 轮结束 / 第 N+1 轮开始 / 进行中看门狗定时扫描）。异步可能"需要时还没生成"，要等待（轮询/WaitGroup/Semaphore）。面试推荐异步生成策略。

细节召回架构

  • 简单方案：ES / 向量库 / 混合检索（做成独立服务或子 Agent：数据同步 + 数据检索两部分）。
  • 数据延迟问题的答案：当轮对话细节不走召回（直接原文），扩展到"当前 K 轮原文传送，K 轮之前走检索"——K 轮间隔足够数据同步完成（K=10，每轮 10 秒也有 100 秒）。
  • 冲突裁决：last win（以最新为主，预算 500 vs 300 取 500）；权威优先（下位政策让步上位政策）；注意"细化/强化"（每周两次周会 vs 一次不是冲突）需在 Prompt 给规则。

暴论：窗口有限 + 摘要 = 细节不可能 100% 不丢

摘要的本质是决策（保留/丢弃/弱化/抽象），一定有信息损失。成熟 Agent 的目标：承认必丢细节，用关键事实提取 + 细节召回 + 冲突裁决 + 模型可读摘要保证"影响决策的细节不丢"。

高级方案

  • 模型可读摘要：把低信息密度表达去掉（礼貌语/转场/口语填充词/铺垫），只留目标、实体、关键事实、硬约束、软偏好、用户确认/否认、数字、时间、决策、理由、风险、缺失信息、证据来源；短句/列表/键值对，不要求流畅。用 flash/mini 生成即可。注意不能随便删"不能/不要/必须/不超过/大概/可能"等承载约束或不确定性的词。Prompt 要求：不得改变原意、不得把不确定改成确定、不得把建议改成已执行、不得把推测改成用户确认、硬约束和用户否认必须显式保留。结合大模型输出摘要 + 滑动窗口使用。
  • 迭代式细节召回：先传索引/目录给大模型 → 模型判定是否缺细节 → 执行细节召回 Action（参数是索引条目）→ 再调用 → 重复直到足够（或让模型说明可忽略哪些细节 / 窗口不够报错）；控制最大迭代次数。实践慎用，面试大胆用。

四、用户画像（上）：建模

核心观点（暴论）

模型能力大家都能用，拉不开差距；用户画像才是私有资产，是 Agent 胜出的杀手锏。"最有性价比"对不同人含义完全不同（大学生=低价能用四年；商务人士=稳定续航信号；摄影爱好者=影像占 60%；苹果生态用户=不换生态）。问题不是模型知不知道哪些手机好，而是 Agent 知不知道什么才叫"对这个用户好"。

反面案例（治好低血压）

永远重复询问（持仓忘掉）、明知道不喜欢还反复推荐、回答正确但牛头不对马嘴（实习生改简历成高级工程师）、输出风格不匹配（理性用户收到幽默文风）、错误画像瞎指导（问一次摄影就标记摄影大师）。

画像维度

维度内容
目标画像用户使用 Agent 的最终目标（雅思 7.5、高考作文 50 分），指导内容生成
能力画像理解能力决定讲多深/多快/什么语言；方案假设的专业程度
偏好画像喜欢什么 + 不喜欢什么（常被忽视；多次表达不喜欢≈硬约束，需在 Prompt 强调）
决策画像用户怎么做选择（先看价格/先看品牌/保守）；决策因子排序，注意场景差异（电子产品性价比优先、衣服外观优先）
关系画像用户与人之间关系（上司 vs 同事邮件语气；社交情感类：谁喜欢谁、信任谁、哪些话不能说）

画像影响范围

影响输入理解（"性价比"）、意图识别与 Slot Filling（"再优化一下"→朝 p7 方向）、上下文选择（按步骤取画像部分）、Plan 与路径选择（用户要快 → 先低风险粗稿）、最终输出（模仿写作风格）。几乎每次大模型调用都应带画像（全量或部分）。

复杂建模示例

用户关系画像（情感/陪聊类）：人物表（person_id/name/aliases/identity/attributes/user_attitude/evidence/confidence）+ 事件表（participants/objective_fact/user_interpretation/user_emotion/relation_effects/source/confidence/status）。要点：区分事实 vs 观点（"用户说老王阴险"记录为用户对老王的态度，不推断老王客观上阴险）；关系有方向（用户对老王 vs 老王对用户）；人物不是静态标签（同事也分很多种）；事件是关系的动态状态，避免单一视角带偏（别一味认同用户判断）。时效性：记录关系变化历史（"最信任"→"背叛后不信任"，覆盖会丢失关键事实）；按需加载当前讨论的人/事件；控制复杂度。

电商用户建模（三层）：全局画像（跨品类成立）→ 品类画像（最重要）：category_id/preference_type/attribute_key/preference_value/preference_mode（喜欢/排斥/硬性）/strength/source/confidence → 当前购物画像。 价格偏好高级设计：品类级价格偏好 = 默认偏好 + 品类偏好；离线计算订单价格百分位数（比"便宜/昂贵"精准）；相似类目价格参考（没买过裤子就参考上衣）。注意事项：购买者 ≠ 使用者（情人节礼物按对象喜好推荐，为相关人独立建模）；浏览记录/购物车只能参考不能全信（满意为何不下单？分析不满意的原因）；需求规格说明：按用户偏好生成推荐规格，广告商品可轻微违反（心理价位 300-500 夹带 250/600 可以），生成广告约束。

五、用户画像（下）：来源、提取与稳定性

层级用户画像（避免把一时兴起当长期）

长期画像（稳定偏好）← 候选/中期画像（有待验证）← 当前画像（本轮对话表现，可覆盖长期）。当前画像覆盖长期画像（长期喜欢苹果、这次明确喜欢小米）。

画像来源（四类）

  1. 用户明确表达：置信度高但不一定长期有效（"回答简单一点"可能只是当下着急）；小心用户撒谎/推脱（"帮朋友问的"）；
  2. 行为推断：行为数据丰富但做了 ≠ 喜欢（买低价手机可能是买给父母；退黑色衣服可能是尺寸不合）——必要时重新审视；
  3. 多轮对话提取：区分说了什么/拒绝了什么/最终选了什么/为什么做此选择（"为什么"偏好意味最强；最终选择可能是无奈的折中而非真喜欢）；
  4. 外部业务系统：接入已有画像，可能需要中间转换。所有画像只是在一定程度上可信。

提取时机（三种 + 混合）

  • 实时提取：每轮结束后立即判断，生成当前画像（及时但易把一时表达当长期）；适合当前画像，不轻易改长期；
  • 对话结束后提取：分析完整过程（最初表达 → 中途修改 → 最终选择），区分"折中妥协"与真喜欢；
  • 离线提取：定期分析（每天），发现趋势、合并重复画像、判断稳定性（半年三次小屏偏好才稳定）、降低长期未出现画像的置信度、识别并裁决冲突、淘汰过期画像（分部分淘汰，理财部分久未使用就淘汰理财）；
  • 实时 + 离线混合：实时保证及时性（只影响当前对话），离线保证准确性（沉淀规律）。

生命周期控制

激活（活跃默认偏好）→ 弱化（长期无新证据或相反行为，用于非敏感场景如 RAG 排序）→ 过期（超过有效期默认不用）。示例：每 3 个月无新证据降级，连续两个季度无证据过期。面试可加状态、加时间控制（激活→弱化 3 个月，弱化→过期半年）。

冲突裁决原则

当前明确表达 > 历史推断；用户明确表达 > 行为推断（买了 3 个苹果后说不再喜欢，信表达）；用户纠正优先（"不是价格敏感，只是这次预算低"→删除价格敏感，保留当前任务预算低）；领域画像 > 全局画像（勤俭节约的人买电子产品拉满配置）。

4C 稳定性评分（区分一时兴起）

stability_score = w0·次数 + w1·持续时间 + w2·跨场景 + w3·用户确认（各项满分 25，默认权重 1）：

  • Count（出现次数）：强调独立会话（一轮里说 5 次 ≠ 5 次独立表达）；count_score = 25 × (1 - e^(-n/3)) 幂饱和——第 15 次不比第 14 次多多少信息；
  • Continuity（持续时间）：25 × min(1, ln(1+d)/ln(1+H))，H=180 天（心理学：激情约 90 天，超 90 天仍喜欢才是真喜欢）；
  • Cross-context（跨场景一致性）：25 × min(1, max(0, s-1)/4)，s 为独立会话数（买手机/电脑/平板都轻便才是真轻便，否则限定领域）；
  • Confirmation（用户确认）：没有确认 0 / 未反对未承认 0-5 / "对，差不多" 10 / 明确确认某场景 20 / 确认长期成立 25（直接问用户）。

使用标准：0-29 candidate（仅保留不影响结果）；30-49 weak（只排序参考）；50-69 active（可影响推荐，不能硬过滤）；70-84 stable（默认偏好）；85-100 confirmed stable（稳定使用但服从当前输入）。面试优化话术：调整 4C 权重（用户确认权重 1→1.5）用 AB 测试验证。

六、长任务：对话/任务特别长怎么办

长任务本质

长任务问题 = 上下文管理问题。难的不是步骤/工具多，而是：不断产生新信息（目标改、Plan 废、输入输出杂、证据良莠不齐）、信息之间的依赖关系（早期不起眼的判断成为后面十几个步骤的前提；早期一句要求变成末尾关键约束）。模型推理能力不可控且窗口有限，你能控制的只有信息取舍。

各类"漂移"（面试被问"漂移"时的弹药）

  • 目标漂移（Goal Context 管理不善：修空指针结果重构几十个文件）；
  • 约束漂移（Constraint Context：要求不虚构却补上"千万级用户"）；
  • 状态漂移（Task State：迁移失败却标记成功）；
  • 证据漂移（Evidence：两年前的文档结论，原文丢弃后坚称最新版不支持）；
  • 细节丢失（压缩不当："绝对不能修改"变成"尽量少修改"）；
  • 错误累积（Observation：累计用户数看成日活，后续全部基于错误数据）。

基础解决方案

  • Plan 模式 → Checkpoint 定期校准：关键节点完成后暂停检查（原始目标/硬约束/任务状态/中间结果证据/原计划是否适用/是否 Retry、Rollback、Replan）。Checkpoint 放在：业务阶段结束、关键中间产物生成、高风险工具调用、被大量后续步骤依赖的节点后。价值：阻止小错误被后续几十个步骤放大。
  • ReAct Loop → 每轮回答"我还差什么"：循环开始/结束（Observation）两个检查点，只查五个维度：目标判断、状态判断、约束判断、差距判断（还差什么——比"我得到了什么"更重要）、证据判断。例子：查到营收降 20%，差的 ReAct 说"分析原因"，好的 ReAct 说"还需看销量/价格/成本/地区/产品线判断来自销量还是单价变化"。ReAct 的本质 = 找数据缺口。

高级解决方案（三种可组合）

  1. 上下文健康检查与漂移检测（Context Verifier）：独立的异步检查器（把 Checkpoint/每轮检查异步化），检查 Goal 偏离、硬约束丢失弱化、Task State 不一致、结论无 Evidence、窗口混入过期重复冲突信息、Observation 被当确定事实；发现问题不直接重跑，输出漂移类型/影响范围/修复建议（召回上下文、修正状态、回滚、局部 Replan）。触发时机：阶段结束、上下文占用达阈值、Replan 前后、异常信号。可类比各种 Verifier（Plan Verifier 等）。
  2. 事件溯源与可信快照：不维护单一被覆盖的当前状态，而是按时间顺序记录关键事件（用户新增/修改约束、完成步骤、工具 Observation、事实确认、结论推翻、Replan 修改）；关键节点生成可信快照，当前状态 = 最近快照 + 后续事件重建。可追溯：跑偏时定位是哪次状态更新/摘要压缩/Observation 引入错误，回到最近可信快照丢弃污染状态重执行。适合状态漂移、证据漂移、错误累积。
  3. 分阶段执行与上下文交接（违背单 Agent 优先原则，慎用）：拆成需求分析/信息收集/方案生成/执行/验证等阶段，每阶段只带局部上下文；阶段结束生成结构化交接信息（总目标、已完成、已确认事实、仍有效硬约束、关键证据及索引、未解决问题、下阶段输入）；临时 Observation 留原阶段按需召回。难点是交接粒度（太少丢细节、太多退化成全量塞入），兜底：下阶段发现不足时回上一阶段召回。

综合混合方案：分阶段控制规模 + 事件溯源保存历史 + Context Verifier 定期检查。目标不是永远不出错，而是更早发现、更准定位、更快从可信状态恢复（面试要点：强调可恢复，且从中间可信状态恢复）。

七、面试竞争力方案

基础策略：五个问题（有什么 / 怎么存 / 怎么找 / 怎么压缩 / 怎么召回）

  1. 有什么：结合业务挑核心几类（会话历史、用户画像、目标约束、候选集与知识、Plan 与中间结果、Action 结果、已确认/否定事实）——让面试官意识到上下文不只是聊天记录；可设计特殊内容（社交情感类加情绪描述）显懂业务；
  2. 怎么存：内存/Redis/MySQL/ES/向量库/对象存储按结构+生命周期选；强调存储层 ≠ 上下文窗口（库可存很多，每次只选一小部分）；
  3. 怎么找：内存 GET、Redis 命令、MySQL SQL（WHERE uid=xxx）、ES/向量库查询（可让大模型撰写查询语句，封装而不是通用 SQL 执行器）——证明检索不是简单的"输入向量化后 Top-K"；
  4. 怎么压缩：不同内容不同处理（硬约束不管多长都保留）；压缩不搞一刀切（区分普通/关键上下文；目标、硬约束、任务状态、关键证据独立维护，不完全依赖摘要）；
  5. 怎么召回：所有被压缩内容保留原始数据和索引，摘要不足时重新召回（指代消解/事实判断/错误定位场景）。

基础话术："我们不会简单把所有历史对话放进 Prompt……根据数据结构和生命周期分别存放……每次调用前根据意图和执行步骤通过结构化查询、关键词检索和向量检索找出候选上下文……窗口不足时普通历史对话摘要、工具结果抽取关键字段，但目标、硬约束和关键任务状态独立保留；摘要不删除原始数据，需要时召回原文、工具结果和中间产物。"

高级策略：围绕一个业务问题设计独特机制（不要背名词）

推荐问题："在有限上下文窗口中，如何既保留稳定的用户偏好，又适应用户临时变化，同时避免压缩后丢失关键细节？" —— 用户画像（分层+4C 判定升级）→ 分层上下文组织 → 动态编排决定本轮放什么 → 差异化压缩解决窗口不足 → 细节召回找回丢失内容；冲突时先召回判断是长期变化/场景差异/临时兴趣，无法确定则向用户澄清而不是覆盖画像。
